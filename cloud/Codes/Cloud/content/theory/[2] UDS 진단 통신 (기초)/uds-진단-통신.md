# [2] UDS 진단 통신 (기초)

- **대상** : 전사 임직원 (구매/재경/인사/법무 등 비전공 직군)
- **목표** : 우리 회사 제품이 무엇을 하는 물건인지, 왜 그것이 중요한지 이해하기

---

## 들어가기 전에

**이 문서를 읽고 나면 알 수 있는 것**

- 우리 회사가 만드는 "진단기"가 정확히 무슨 일을 하는 장비인지
- 정비소에서 자동차를 고칠 때 실제로 어떤 일이 벌어지는지
- 사내에서 자주 들리는 UDS, ECU, DTC, 플래싱 같은 용어의 의미

**이 문서에서 다루지 않는 것**

- 실제 통신 코드와 바이트 단위 구조 (심화 자료에서 다룹니다)
- 개발 실무에 필요한 구현 방법 및 시나리오

---

## 1. UDS 개요 — 자동차와 대화하는 방법

### 1.1 자동차 안에는 컴퓨터가 100개쯤 있다

**ECU란 무엇인가**

- ECU = Electronic Control Unit, 우리말로 **전자제어장치**
- 쉽게 말해 **자동차 부품마다 붙어 있는 작은 컴퓨터**
- 엔진, 브레이크, 에어백, 창문, 시트, 헤드라이트 등 거의 모든 기능마다 존재

**규모 감각**

| 시기 | 차량 1대당 ECU 수 | 참고 |
| --- | --- | --- |
| 1990년대 | 5~10개 | 엔진 제어 위주 |
| 2010년대 | 50~70개 | 편의장치 확대 |
| 현재 | 100개 이상 | 자율주행·인포테인먼트 추가 |

- 최신 차량의 소프트웨어 코드 양은 **여객기보다 많습니다**
- 즉, 오늘날 자동차는 "바퀴 달린 컴퓨터 네트워크"에 가깝습니다

---

### 1.2 그래서 문제가 생겼다

**과거의 자동차 정비**

- 엔진 소리를 듣고, 부품을 눈으로 보고, 손으로 만져서 고장을 찾음
- 정비사의 경험과 감각이 핵심

**현재의 자동차 정비**

- 고장의 상당수가 **눈에 보이지 않는 곳**에서 발생
- 예: "엔진 경고등이 켜졌다" → 육안으로는 원인 파악 불가
- 컴퓨터가 문제라면, **컴퓨터에게 직접 물어봐야** 합니다

**여기서 등장하는 것이 진단 통신**

> 정비사가 자동차에게 묻습니다. "지금 어디가 아프니?"
>
> 자동차가 답합니다. "3번 실린더에 문제가 있고, 그건 어제 시속 60km로 달릴 때 처음 생겼어요."

- 이 **질문과 대답을 주고받는 규칙**이 바로 UDS입니다

---

### 1.3 UDS = 자동차와 대화하기 위한 공용어

**UDS의 정의**

- **U**nified **D**iagnostic **S**ervices의 약자
- 우리말로는 **통합 진단 서비스**
- 진단기와 자동차가 대화할 때 쓰는 **표준 언어**

**왜 "통합(Unified)"인가**

- 과거에는 제조사마다 서로 다른 방식을 사용
- 현대차 진단기로는 BMW를 진단할 수 없는 상황
- → 국제 표준으로 통일 (**ISO 14229**, 2006년 제정)
- 이제 어느 제조사든 기본 규칙은 동일

**비유로 이해하기**

| 상황 | 비유 |
| --- | --- |
| 자동차 = 환자 | 어디가 아픈지 스스로 말할 수 있음 |
| ECU = 각 신체 기관 | 각자 자기 상태를 기록하고 있음 |
| 진단기 = 의사 | 질문을 던지고 답을 해석 |
| **UDS = 진료 시 쓰는 공통 의학 용어** | 어느 병원이든 통하는 표준 |

---

### 1.4 대화는 어떻게 이루어지는가

**기본 원칙 : 항상 진단기가 먼저 묻는다**

```
   진단기  ──── "고장 코드 알려줘" ────→   자동차
   진단기  ←──── "3개 있어요" ──────────   자동차
```

- 자동차가 먼저 말을 거는 일은 없습니다
- 반드시 **진단기가 질문 → 자동차가 대답**
- 이런 구조를 전문 용어로 **Client-Server 방식**이라고 합니다

**대답은 두 종류뿐**

| 대답 종류 | 의미 | 일상 비유 |
| --- | --- | --- |
| 긍정 응답 | "네, 요청하신 대로 처리했습니다" | 요청 수락 |
| 부정 응답 | "안 됩니다. 이유는 ○○입니다" | 사유를 붙인 거절 |

- 중요한 점은 **거절할 때 반드시 이유를 알려준다**는 것
- 이 거절 사유 코드를 **NRC**라고 부릅니다 (2장에서 설명)

---

## 2. UDS 메커니즘 — 아무나 아무거나 할 수는 없다

### 2.1 왜 제약이 필요한가

**만약 아무 제약이 없다면**

- 주행 중인 차량의 엔진 소프트웨어를 누군가 지워버릴 수 있음
- 도난 방지 장치를 무력화할 수 있음
- 차량 정보를 마음대로 위조할 수 있음

**따라서 UDS는 3중 잠금 장치를 둡니다**

| 잠금 장치 | 역할 | 일상 비유 |
| --- | --- | --- |
| **세션(Session)** | 지금 어떤 모드인지 | 은행 창구 vs 금고실 |
| **보안 접근** | 권한이 있는 사람인지 | 신분증 확인 |
| **조건 확인** | 지금 해도 되는 상황인지 | 주행 중에는 불가 |

---

### 2.2 세션 — 모드를 바꿔야 할 수 있는 일이 늘어난다

**세션이란**

- 자동차가 현재 어떤 **진단 모드**에 있는지를 뜻함
- 모드에 따라 할 수 있는 일이 달라짐

**세 가지 주요 모드**

| 모드 | 이름 | 할 수 있는 일 | 비유 |
| --- | --- | --- | --- |
| 기본 | Default | 간단한 정보 읽기만 | 은행 로비 |
| 확장 | Extended | 고장 코드 조회·삭제, 부품 동작 테스트 | 창구 상담 |
| 프로그래밍 | Programming | 소프트웨어 교체 | 금고실 |

**핵심 규칙**

- 자동차는 시동을 걸면 **항상 기본 모드**로 시작
- 더 많은 일을 하려면 진단기가 **모드 전환을 요청**해야 함
- 위험한 작업일수록 더 높은 모드가 필요

**모드는 저절로 풀린다**

- 진단기가 5초 정도 아무 말도 안 하면 자동으로 기본 모드로 복귀
- 그래서 진단기는 **"저 아직 여기 있어요"** 신호를 2초마다 계속 보냅니다
- 이 신호를 **TesterPresent**라고 부릅니다

> **왜 이런 설계인가** 정비사가 진단기를 꽂아둔 채 자리를 비웠는데 차가 계속 위험한 모드로 남아 있으면 안 되기 때문입니다.

---

### 2.3 보안 접근 — 열쇠 없이는 못 들어간다

**Seed & Key 방식**

- 중요한 작업을 하려면 자동차가 **암호 문제를 냅니다**
- 정답을 맞혀야만 권한이 열립니다

```
   진단기 : "권한 좀 주세요"
   자동차 : "그럼 문제 낼게요. 12345678"      ← Seed(씨앗)
   진단기 : (비밀 계산식 적용) "답은 ABCD입니다"  ← Key(열쇠)
   자동차 : "정답입니다. 권한 드릴게요"
```

**핵심 포인트**

- 계산식은 **제조사만 알고 있는 비공개 정보**
- 그래서 정품 진단기가 아니면 자동차를 조작할 수 없습니다
- 3번 틀리면 일정 시간 동안 시도 자체가 차단됩니다

> **업무 연결 포인트** 이 계산식을 자동차 제조사로부터 받는 것이 진단기 회사의 핵심 자산입니다. 계약·보안 관리의 중요한 대상이며, 유출 시 심각한 문제가 됩니다.

---

### 2.4 조건 확인 — 지금은 안 됩니다

**자동차가 거절하는 대표적 상황**

| 상황 | 거절 사유 |
| --- | --- |
| 차가 움직이는 중 | 주행 중에는 위험한 작업 불가 |
| 기어가 P가 아님 | 안전 조건 미충족 |
| 배터리 전압이 낮음 | 작업 도중 전원이 끊길 위험 |
| 엔진이 켜져 있음/꺼져 있음 | 작업 종류에 따라 요구 조건이 다름 |

**NRC (거절 사유 코드)**

- 자동차는 거절할 때 **왜 거절하는지 코드로 알려줍니다**
- 진단기는 이 코드를 보고 정비사에게 안내 메시지를 표시

```
   진단기 표시 예시

   "차량 속도가 0이 아닙니다. 차량을 완전히 정지시킨 후
    기어를 P에 놓고 다시 시도해 주세요."
```

- 이 안내를 얼마나 친절하고 정확하게 만드느냐가 **진단기 제품 경쟁력**의 일부입니다

---

## 3. UDS 주요 서비스 상세 - 1 : 상태를 읽는 기능

### 3.1 서비스란

- UDS에서 **"진단기가 자동차에게 시킬 수 있는 일의 목록"**
- 국제 표준에 약 26가지가 정의되어 있음
- 각 서비스에는 고유 번호가 붙어 있음 (예: 0x19, 0x22)
- 사내에서 "22 서비스", "19 서비스"라고 부르는 것이 이것입니다

---

### 3.2 고장 코드 읽기 — 가장 자주 쓰이는 기능

**DTC란**

- **D**iagnostic **T**rouble **C**ode, 우리말로 **고장 진단 코드**
- 자동차가 이상을 감지했을 때 **스스로 기록해두는 코드**
- 계기판의 **엔진 경고등**이 켜지는 이유가 바로 이것

**DTC 코드 읽는 법**

```
   P 0 3 0 1
   │
   └─ 첫 글자가 어느 영역인지 알려줍니다
```

| 첫 글자 | 영역 | 예시 |
| --- | --- | --- |
| **P** | Powertrain (엔진·변속기) | P0301 = 3번 실린더 점화 실패 |
| **C** | Chassis (섀시·제동) | C1234 |
| **B** | Body (편의장치) | B1234 |
| **U** | Network (통신) | U0100 |

**고장 코드에는 상태 정보도 함께 붙습니다**

| 상태 | 의미 |
| --- | --- |
| 확정 (Confirmed) | 확실한 고장으로 판정됨 |
| 대기 (Pending) | 한 번 발생했으나 아직 확정 전 |
| 현재 발생 중 | 지금 이 순간에도 문제가 있음 |

> **왜 이 구분이 중요한가** "한 번 튀었던 것"과 "지속적인 고장"을 구분해야 불필요한 부품 교체를 막을 수 있습니다. 소비자 분쟁이나 보증 처리에서도 근거 자료가 됩니다.

---

### 3.3 스냅샷 — 고장 났던 순간의 사진

**Snapshot Data**

- 고장이 발생한 **그 순간의 차량 상태**를 자동으로 저장
- 저장되는 항목 예시: 엔진 회전수, 차량 속도, 냉각수 온도, 연료량

**비유**

> 블랙박스가 사고 순간을 녹화하듯, 자동차는 고장 순간의 상태를 저장해 둡니다.

**실무 가치**

- "재현이 안 되는 고장"을 분석할 수 있는 유일한 단서
- 고객이 "가끔 그래요"라고 말할 때 정비사가 기댈 수 있는 근거

---

### 3.4 정보 읽기 — 신분증 확인

**진단기가 자동차에게서 읽어오는 대표 정보**

| 정보 | 설명 |
| --- | --- |
| **VIN** | 차대번호. 차량마다 고유한 17자리 식별번호 |
| 소프트웨어 버전 | 현재 설치된 프로그램 버전 |
| 하드웨어 번호 | 부품 자체의 품번 |
| ECU 제조일 / 시리얼 | 생산 이력 |

> **업무 연결 포인트** VIN은 차량의 주민등록번호에 해당합니다. 리콜 대상 판별, 보증 기간 확인, 중고차 이력 조회가 모두 VIN을 기준으로 이루어집니다.

---

### 3.5 고장 코드 삭제와 재시작

**고장 코드 삭제**

- 정비 완료 후 기록된 고장 코드를 지우는 기능
- 경고등이 꺼집니다
- 단, **원인을 고치지 않고 지우기만 하면 다시 켜집니다**

**ECU 재시작**

- 자동차의 컴퓨터를 껐다 켜는 기능
- 소프트웨어 교체 후 새 버전을 적용할 때 필수

---

## 4. UDS 주요 서비스 상세 - 2 : 차량을 바꾸는 기능

### 4.1 읽기와 쓰기의 차이

| 구분 | 위험도 | 필요 권한 |
| --- | --- | --- |
| **읽기** (상태 조회) | 낮음 | 대부분 제약 없음 |
| **쓰기** (변경·제어) | 높음 | 보안 인증 + 조건 충족 필수 |

- 3장이 "읽기"였다면, 4장은 **"쓰기"** 입니다
- 여기서부터는 자동차의 동작이 실제로 바뀝니다

---

### 4.2 부품 강제 동작 — 진짜로 움직여보기

**액추에이터 테스트**

- 진단기가 자동차 부품을 **직접 강제로 작동**시키는 기능
- 예시: 헤드라이트 강제 점등, 연료 펌프 강제 구동, 냉각 팬 강제 회전

**왜 필요한가**

```
   증상 : 헤드라이트가 안 켜진다

   원인 후보 1 : 전구 자체가 나감
   원인 후보 2 : 스위치 고장
   원인 후보 3 : 배선 단선
   원인 후보 4 : 제어 컴퓨터 고장

   → 진단기로 강제 점등을 시도해서 원인을 좁혀 나갑니다
```

**안전 장치**

- 일정 시간이 지나면 자동차가 **제어권을 자동으로 회수**
- 진단기 연결이 끊기면 즉시 원상 복구
- 주행 중에는 위험한 항목의 제어가 아예 차단됨

---

### 4.3 데이터 쓰기 — 정보를 바꾸는 일

**대표 사례**

| 작업 | 상황 |
| --- | --- |
| VIN 등록 | ECU를 새 부품으로 교체했을 때 |
| 정비 이력 기록 | 어느 정비소에서 언제 작업했는지 |
| 사양 설정 변경 | 지역별·트림별 옵션 반영 |

- 모두 **보안 인증을 통과해야만** 가능합니다

---

### 4.4 플래싱 — 자동차의 소프트웨어 교체

**플래싱(리프로그래밍)이란**

- 자동차 컴퓨터의 **프로그램 자체를 새 버전으로 교체**하는 작업
- 스마트폰 OS 업데이트와 같은 개념

**언제 필요한가**

| 상황 | 설명 |
| --- | --- |
| 결함 수정 | 소프트웨어 버그로 인한 리콜 대응 |
| 기능 개선 | 연비 향상, 변속 로직 개선 |
| 부품 교체 | 새 ECU에 해당 차량용 프로그램 설치 |

**작업 순서 (개념)**

```
   [1] 안전 조건 확인   차 정지, 기어 P, 배터리 충분
   [2] 권한 획득        보안 인증 통과
   [3] 기존 내용 삭제   메모리 비우기
   [4] 새 내용 전송     데이터를 조각내어 순차 전송
   [5] 검증             제대로 들어갔는지 확인
   [6] 재시작           새 버전 적용
```

**왜 이 작업이 위험한가**

> 4번 단계 도중에 전원이 끊기면 자동차 컴퓨터가 **아무 프로그램도 없는 상태**가 됩니다. 시동이 걸리지 않고, 전용 장비로 복구하거나 부품을 교체해야 합니다.

- 그래서 플래싱 중에는 배터리 충전기를 반드시 연결합니다
- 진단기 제품의 **안정성이 가장 중요하게 평가되는 기능**이 바로 이것입니다

---

### 4.5 전송 속도가 왜 사업적으로 중요한가

**같은 작업, 다른 소요 시간**

| 통신 방식 | 1MB 소프트웨어 전송 | 비고 |
| --- | --- | --- |
| CAN | 약 30분 ~ 1시간 | 기존 방식 |
| CAN FD | 약 5 ~ 10분 | 개선 방식 |
| **이더넷 (DoIP)** | **약 30초 ~ 1분** | 최신 방식 |

**사업적 함의**

| 관점 | 영향 |
| --- | --- |
| 생산 라인 | 차 1대당 작업 시간이 라인 속도를 결정 |
| A/S 센터 | 정비 1건당 소요 시간 = 인건비 = 수익성 |
| 리콜 대응 | 수만 대 대상 리콜 시 총 비용에 직결 |
| 제품 경쟁력 | "우리 진단기가 더 빠릅니다"가 곧 수주 논리 |

> 최신 차량은 소프트웨어 용량이 수십 MB 이상입니다. 위 표의 시간에 수십 배를 곱하면 왜 업계가 이더넷 방식으로 전환하는지 이해할 수 있습니다.

## 5. UDS 시나리오 예제 — 실제로는 이렇게 흘러갑니다

### 5.1 시나리오 1 : 정비소에서 경고등 진단

**상황** : 고객이 "엔진 경고등이 켜졌다"며 입고

```
   [1] 진단기를 차량 커넥터에 연결
   [2] 진단 모드 진입 요청
   [3] "고장 코드 몇 개 있니?"        → "3개요"
   [4] "목록 알려줘"                  → P0301, P0420, C1234
   [5] "P0301 발생 당시 상황은?"      → RPM 1800, 60km/h, 90도
   [6] 정비사가 원인 분석 후 부품 교체
   [7] 고장 코드 삭제                 → 경고등 소등
   [8] 시운전 후 재발 여부 확인
```

**소요 시간** : 진단 통신 자체는 수 초 ~ 수십 초

---

### 5.2 시나리오 2 : 소프트웨어 업데이트(리콜 대응)

**상황** : 제조사가 결함 수정 리콜을 발표, 정비소에서 대응

```
   [1] 차량 정지, 기어 P, 배터리 충전기 연결
   [2] 현재 소프트웨어 버전 확인
   [3] 다른 부품들의 통신을 잠시 차단   ← 간섭 방지
   [4] 프로그래밍 모드 진입
   [5] 보안 인증 통과
   [6] 기존 프로그램 삭제
   [7] 새 프로그램 전송              ← 가장 오래 걸리는 구간
   [8] 검증
   [9] 컴퓨터 재시작
   [10] 새 버전 확인 및 통신 복원
```

**주의 사항**

- 이 과정에서 **절대 진단기를 뽑거나 시동을 끄면 안 됩니다**
- 전체 소요 시간의 대부분이 [7]번 구간

---

### 5.3 시나리오 3 : 생산 라인에서의 검사

**상황** : 공장에서 갓 조립된 차량의 전수 검사

```
   [1] 차량이 검사 구역 진입
   [2] 진단기 자동 연결
   [3] 모든 컴퓨터에 "정상이니?" 일괄 질문
   [4] VIN 등 차량 고유 정보 기록
   [5] 각 부품 강제 동작 테스트 (라이트, 와이퍼 등)
   [6] 검사 중 발생한 고장 코드 삭제
   [7] 합격 판정 후 다음 공정으로
```

**특징**

- 하루 수백~수천 대를 처리하므로 **속도가 절대적으로 중요**
- 차 1대당 몇 초를 줄이느냐가 공장 전체 생산량을 좌우

---

### 5.4 통신 방식은 계속 발전하고 있습니다

| 세대 | 방식 | 특징 |
| --- | --- | --- |
| 1세대 | K-Line | 매우 느림, 제조사마다 제각각 |
| 2세대 | **CAN** | 현재 가장 널리 쓰임 |
| 3세대 | CAN FD | CAN의 속도 개선판 |
| 4세대 | **이더넷 (DoIP)** | 인터넷 기술 활용, 확산 중 |

**중요한 점**

> 통신 방식이 바뀌어도 **UDS라는 대화 규칙은 그대로**입니다. 편지를 우편으로 보내든 이메일로 보내든, 편지에 쓰는 언어는 같은 것과 비슷합니다.

**앞으로의 방향**

- **원격 진단** : 정비소에 가지 않고 통신망으로 진단
- **무선 업데이트(OTA)** : 스마트폰처럼 자동차도 무선으로 업데이트
- 두 가지 모두 이더넷 기반 진단 기술이 전제 조건입니다

## 6. [부록] 용어 정리 및 업무 연결

### 6.1 회의에서 자주 들리는 용어

| 용어 | 의미 |
| --- | --- |
| **UDS** | 진단 통신 표준 언어 |
| **ECU** | 자동차 부품에 붙은 소형 컴퓨터 |
| **DTC** | 고장 진단 코드 |
| **VIN** | 차대번호 (17자리) |
| **Tester** | 진단기 (우리 제품) |
| **플래싱** | 자동차 소프트웨어 교체 작업 |
| **세션** | 진단 모드 (기본/확장/프로그래밍) |
| **NRC** | 자동차가 요청을 거절한 사유 코드 |
| **SID** | 서비스 번호 (기능마다 부여된 고유 번호) |
| **DID** | 데이터 번호 (정보마다 부여된 고유 번호) |
| **DoIP** | 이더넷 기반 진단 통신 방식 |
| **CAN** | 현재 가장 널리 쓰이는 차량 통신 방식 |
| **OTA** | 무선 소프트웨어 업데이트 |

---

### 6.2 관련 국제 표준

| 표준 | 내용 | 알아둘 점 |
| --- | --- | --- |
| **ISO 14229** | UDS 규격 본체 | 우리 제품의 기술적 근거 |
| **ISO 15765** | CAN 기반 진단 전송 | 기존 방식 |
| **ISO 13400** | 이더넷 기반 진단 전송 (DoIP) | 차세대 방식 |
| **UN R155 / R156** | 차량 사이버보안·업데이트 관리 법규 | **권고가 아닌 강제 법규** |

> **법무·인증 담당자 참고** UN R155/R156은 유럽을 중심으로 형식승인의 필수 요건입니다. 미충족 시 차량 판매 자체가 불가하므로, 관련 대응 여부가 고객사와의 계약 조건에 포함되는 경우가 있습니다.

---

### 6.3 한 장 요약

```
  자동차 안에는 컴퓨터(ECU)가 100개 이상 있다
                    ↓
  고장 나면 눈으로는 알 수 없다
                    ↓
  컴퓨터에게 직접 물어봐야 한다
                    ↓
  물어보는 표준 언어가 UDS
                    ↓
  그 언어로 대화하는 장비가 진단기 = 우리 제품
                    ↓
  읽기(고장 조회) + 쓰기(부품 제어, 소프트웨어 교체)
                    ↓
  위험한 작업일수록 모드 전환·보안 인증·조건 확인이 필요
                    ↓
  통신 속도가 곧 정비 시간이고, 정비 시간이 곧 비용이다
                    ↓
  그래서 업계는 더 빠른 이더넷 방식(DoIP)으로 이동 중
```
