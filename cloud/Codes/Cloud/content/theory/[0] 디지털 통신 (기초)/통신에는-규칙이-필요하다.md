# (3) 통신에는 규칙이 필요하다

- **선수 학습** : 1~2장
- **이 장의 목표** : UDS와 DoIP의 관계를 이해할 수 있는 사고 틀 갖추기

> **이 장은 이 자료에서 가장 중요합니다.** 여기서 배우는 개념이 [2] UDS와 [4] DoIP 자료 전체를 관통합니다.

---

## 3.1 약속이 없으면 대화가 안 된다

### 생각해볼 상황

```
   두 사람이 만났습니다.

   A는 한국어만 할 줄 압니다.
   B는 스페인어만 할 줄 압니다.

   → 서로 소리는 내고 있지만 대화가 되지 않습니다
```

- 소리가 전달되지 않은 것이 아닙니다
- **전달은 되었지만 해석할 수 없는** 것입니다

### 컴퓨터도 똑같습니다

```
   진단기가 보낸 것 : 0과 1의 나열
   자동차가 받은 것 : 0과 1의 나열

   그런데 이게 무슨 뜻인가?
```

- 0과 1을 주고받는 것만으로는 아무 의미가 없습니다
- **"이 자리의 값은 이런 뜻이다"** 라는 약속이 있어야 합니다

### 프로토콜 = 통신 규칙

- 이 약속을 **프로토콜(Protocol)** 이라고 부릅니다
- 우리말로는 **통신 규약** 또는 **통신 규칙**

**프로토콜이 정하는 것**

| 항목 | 예시 |
| --- | --- |
| 누가 먼저 말하는가 | 진단기가 먼저 질문 |
| 어떤 순서로 보내는가 | 앞자리는 요청 종류, 뒷자리는 대상 |
| 각 값이 무슨 뜻인가 | 특정 값 = 특정 요청 |
| 대답은 어떻게 하는가 | 성공/실패를 구분해서 |
| 실패하면 어떻게 알리는가 | 사유를 코드로 전달 |

> **자동차와의 연결** 앞으로 배울 **UDS**가 바로 이 프로토콜 중 하나입니다. 진단기와 자동차가 대화할 때 쓰는 약속입니다.

---

## 3.2 요청과 응답

### 가장 기본적인 대화 구조

```
   [질문하는 쪽]  ────── 요청 ──────→  [대답하는 쪽]
   [질문하는 쪽]  ←───── 응답 ───────  [대답하는 쪽]
```

- 대부분의 통신은 이 구조를 씁니다
- 우리 일상과 다르지 않습니다

**일상 사례**

| 상황 | 요청 | 응답 |
| --- | --- | --- |
| 웹사이트 접속 | "이 페이지 주세요" | 페이지 전송 |
| 카드 결제 | "5만원 결제해주세요" | 승인 / 거절 |
| ATM | "잔액 알려주세요" | 잔액 표시 |

### 누가 먼저 말하는지 정해두는 이유

```
   만약 양쪽이 동시에 말하면?

   진단기 : "고장 코드 알려줘"
   자동차 : "지금 온도가 90도야"

   → 서로의 말이 섞여서 알아들을 수 없습니다
```

- 그래서 **한쪽이 물어보고, 다른 쪽이 답하는** 구조로 정해둡니다
- 진단 통신에서는 **진단기가 항상 먼저** 질문합니다

### 응답은 두 종류

| 응답 | 의미 |
| --- | --- |
| **긍정 응답** | "요청대로 처리했습니다" |
| **부정 응답** | "못 합니다. 이유는 ○○입니다" |

**거절할 때 이유를 알려주는 것이 중요합니다**

```
   [나쁜 설계]
   자동차 : "안 됩니다"
   → 왜 안 되는지 알 수 없어 무엇을 고쳐야 할지 모름

   [좋은 설계]
   자동차 : "안 됩니다. 차량이 주행 중이기 때문입니다"
   → 차를 세우고 다시 시도하면 됨
```

- 잘 만든 프로토콜은 **실패 사유를 구체적으로 알려줍니다**
- 진단기는 이 사유를 사람이 읽을 수 있는 안내 문구로 바꿔 보여줍니다

## 3.3 표준이 필요한 이유

### 표준이 없으면 벌어지는 일

```
   A사 자동차 : A사 진단기로만 진단 가능
   B사 자동차 : B사 진단기로만 진단 가능
   C사 자동차 : C사 진단기로만 진단 가능

   → 정비소는 진단기를 회사 수만큼 사야 합니다
```

**실제로 과거에 이랬습니다**

| 문제 | 결과 |
| --- | --- |
| 제조사마다 방식이 다름 | 정비소 장비 구입 부담 |
| 진단기 회사도 제각각 대응 | 개발 비용 증가 |
| 정비사도 방식마다 따로 학습 | 숙련까지 오래 걸림 |

### 표준화가 가져온 변화

- 국제 기구가 **공통 규격**을 정했습니다
- 이제 기본 규칙은 어느 제조사든 동일합니다

```
   [표준 이전]                [표준 이후]

   A사 방식                   공통 표준
   B사 방식      →            (+ 제조사별 일부 고유 영역)
   C사 방식
```

**표준의 효과**

| 관점 | 효과 |
| --- | --- |
| 정비소 | 진단기 한 대로 여러 제조사 대응 |
| 진단기 회사 | 하나의 기반 위에 제품 개발 |
| 자동차 제조사 | 검증된 규격 활용 |
| 소비자 | 정비 선택권 확대 |

### 표준은 문서로 존재합니다

- 국제표준화기구(ISO)가 발행하는 문서에 규정되어 있습니다
- 사내에서 `ISO 14229`, `ISO 13400` 같은 번호가 나오는 이유입니다

| 번호 | 내용 |
| --- | --- |
| ISO 14229 | 진단 대화 언어 (UDS) |
| ISO 13400 | 이더넷 기반 진단 전송 (DoIP) |
| ISO 15765 | CAN 기반 진단 전송 |

> **다만 표준이 전부를 정하지는 않습니다.** 보안 관련 부분 등은 제조사가 각자 정하도록 남겨두었습니다. 그래서 진단기 회사는 제조사별 정보를 별도로 확보해야 합니다.

## 3.4 내용과 전달 수단은 별개다

> **이 절이 3장의 핵심입니다.**

### 편지를 생각해봅시다

```
   편지에는 두 가지가 있습니다

   [1] 편지에 쓴 내용    ← 무엇을 전하고 싶은가
   [2] 보내는 방법       ← 어떻게 전달할 것인가
```

**이 둘은 서로 독립적입니다**

| 내용 | 전달 방법 | 가능한가 |
| --- | --- | --- |
| "안녕하세요" | 우편 | 가능 |
| "안녕하세요" | 이메일 | 가능 |
| "안녕하세요" | 팩스 | 가능 |

- 전달 방법을 바꿔도 **편지 내용은 그대로**입니다
- 반대로 내용을 바꿔도 **우편 시스템은 그대로**입니다

### 이것을 계층이라고 부릅니다

```
   ┌─────────────────────┐
   │  내용 (무엇을)       │   ← 위층
   ├─────────────────────┤
   │  전달 (어떻게)       │   ← 아래층
   └─────────────────────┘

   위층은 아래층이 어떻게 배달하는지 신경 쓰지 않습니다
   아래층은 위층이 무슨 내용인지 신경 쓰지 않습니다
```

**각 층이 자기 일만 하면 됩니다**

| 층 | 관심사 | 관심 없는 것 |
| --- | --- | --- |
| 내용 | 무엇을 전할 것인가 | 우편인지 이메일인지 |
| 전달 | 어떻게 배달할 것인가 | 편지에 뭐라고 썼는지 |

### 왜 이렇게 나누는가

**한쪽을 바꿔도 다른 쪽을 건드리지 않아도 됩니다**

```
   [상황] 우편이 너무 느려서 이메일로 바꾸기로 했다

   바꿔야 할 것 : 전달 방법
   그대로인 것  : 편지 내용, 편지 쓰는 법
```

- 만약 계층이 나뉘어 있지 않았다면 **전부 새로 만들어야** 합니다
- 나뉘어 있으면 **한 층만 교체**하면 됩니다

> **자동차와의 연결** 이것이 바로 UDS와 DoIP의 관계입니다.
>
> | 층 | 담당 |
> | --- | --- |
> | 내용 | **UDS** — 무엇을 물어볼 것인가 |
> | 전달 | **CAN** 또는 **DoIP** — 어떻게 전달할 것인가 |
>
> 전달 방식을 CAN에서 DoIP로 바꿔도 **UDS는 그대로**입니다. 그래서 기존에 쌓은 진단 지식이 그대로 쓸모 있습니다.

## 3.5 우리 주변의 사례

### 사례 1 — 택배

```
   ┌──────────────────────────┐
   │  상자 안의 물건           │  ← 내용
   ├──────────────────────────┤
   │  송장 (받는 사람, 주소)   │  ← 전달 정보
   └──────────────────────────┘
```

**주목할 점**

| 항목 | 설명 |
| --- | --- |
| 택배 기사 | 상자 안에 뭐가 있는지 모름 |
| 보내는 사람 | 트럭이 어느 경로로 가는지 모름 |
| 송장 | 배달에 필요한 정보만 담음 |

- 각자 자기 역할만 하는데 물건은 잘 도착합니다
- 배송사를 바꿔도 상자 안 물건은 그대로입니다

### 사례 2 — 편지 봉투

```
   봉투 겉면 : 주소, 우편번호, 우표     ← 배달에 필요
   봉투 안   : 편지 내용                ← 받는 사람만 봄
```

**여러 겹으로 싸는 경우도 있습니다**

```
   [편지]  →  [봉투]  →  [소포 상자]  →  [화물 컨테이너]

   각 단계마다 그 단계에 필요한 정보가 붙습니다
```

- 통신도 마찬가지로 여러 겹의 정보가 붙습니다
- 이것을 **캡슐화**라고 부릅니다

### 사례 3 — 식당 주문

```
   손님 : "김치찌개 하나요"           ← 요청
   직원 : "네, 15분 걸립니다"         ← 응답

   손님 : "김치찌개 하나요"
   직원 : "죄송합니다. 재료가 떨어졌습니다"   ← 부정 응답 + 사유
```

**이 대화에 프로토콜의 요소가 모두 들어 있습니다**

| 요소 | 사례 |
| --- | --- |
| 누가 먼저 | 손님이 먼저 주문 |
| 요청 | 김치찌개 |
| 긍정 응답 | 가능, 15분 |
| 부정 응답 | 불가, 재료 없음 |
| 사유 전달 | "재료가 떨어졌습니다" |

> 진단 통신도 구조는 이것과 똑같습니다. 다만 한국어 대신 정해진 숫자를 쓸 뿐입니다.

## 3장 정리

| 개념 | 핵심 |
| --- | --- |
| 프로토콜 | 통신에 필요한 약속 |
| 요청-응답 | 한쪽이 묻고 다른 쪽이 답함 |
| 부정 응답 | 거절할 때 **사유를 함께** 전달 |
| 표준 | 제조사가 달라도 통하게 만드는 공통 규격 |
| **계층** | **내용과 전달 수단을 분리하는 것** |

**한 장 요약**

```
   0과 1만 주고받아서는 의미가 없다
                ↓
   "이 값은 이런 뜻이다"라는 약속이 필요하다  = 프로토콜
                ↓
   제조사마다 약속이 다르면 곤란하다          = 표준
                ↓
   내용과 전달 수단은 나눠두는 게 좋다        = 계층
                ↓
   그래야 한쪽만 바꿔도 다른 쪽은 그대로 쓸 수 있다
```

**가장 중요한 한 문장**

```
   무엇을 말하는가(내용)와
   어떻게 전달하는가(수단)는 별개다.
```

---

**다음 장 예고**

> 3장이 "약속"에 관한 이야기였다면, 4장은 **그 신호가 실제로 전선을 타고 어떻게 오가는지**를 다룹니다. 자동차 통신이 왜 그렇게 설계되었는지가 드러납니다.
