# (5) 데이터의 크기와 속도

- **선수 학습** : 1~4장
- **이 장의 목표** : 통신 속도를 스스로 계산해보고, 기술 전환의 이유를 숫자로 이해하기

> **4장에서 남겨둔 질문** "8바이트씩 나눠 보내면 실제로 얼마나 걸릴까?" 이 장에서 직접 계산해봅니다.

---

## 5.1 KB, MB, GB 체감하기

### 단위가 커지는 방식

```
   1 KB (킬로바이트)  =  약 1,000 바이트
   1 MB (메가바이트)  =  약 1,000 KB
   1 GB (기가바이트)  =  약 1,000 MB
   1 TB (테라바이트)  =  약 1,000 GB
```

- 한 단계 올라갈 때마다 **약 1,000배**입니다

> **정확히는 1,024배입니다** 컴퓨터는 2진수를 쓰기 때문에 딱 떨어지는 값이 1,024입니다. 다만 실무에서는 **1,000으로 어림잡아** 계산해도 문제없습니다. 이 자료에서도 1,000 기준으로 설명합니다.

### 얼마나 큰지 감 잡기

| 크기 | 이 정도 |
| --- | --- |
| 1 바이트 | 영어 글자 1개 |
| 100 바이트 | 짧은 문장 하나 |
| 1 KB | A4 반 페이지 분량의 글 |
| 100 KB | 사진 1장 (저화질) |
| 1 MB | 사진 1장 (고화질) |
| 10 MB | 음악 파일 2~3곡 |
| 100 MB | 짧은 동영상 |
| 1 GB | 영화 1편 |

### 자동차 소프트웨어는 얼마나 큰가

| 시기 | 부품 1개당 프로그램 크기 |
| --- | --- |
| 2000년대 초 | 수십 ~ 수백 KB |
| 2010년대 | 수 MB |
| 현재 | 수십 MB 이상 |

```
   과거 : 100 KB   ← A4 50페이지 정도
   현재 : 50 MB    ← 고화질 사진 50장 정도

   약 500배 증가
```

- 자율주행이나 인포테인먼트 관련 부품은 이보다 훨씬 큽니다
- 최신 차량 전체의 소프트웨어를 합치면 **수 GB** 수준입니다

> **4장과의 연결** CAN은 한 번에 **8바이트**를 보냅니다. 50 MB를 8바이트씩 나누면 몇 번이 될까요? 5.3절에서 계산해봅니다.

## 5.2 bps — bit와 Byte는 8배 차이

### 속도의 단위

- **bps** = bits per second
- 우리말로 **초당 비트 수**

```
   1 bps    = 1초에 비트 1개
   1 Kbps   = 1초에 비트 1,000개
   1 Mbps   = 1초에 비트 100만 개
   1 Gbps   = 1초에 비트 10억 개
```

### 여기서 가장 흔한 실수

> **속도는 비트(b), 용량은 바이트(B) 단위입니다.** 이 둘은 **8배** 차이가 납니다.

| 표기 | 읽는 것 | 쓰이는 곳 |
| --- | --- | --- |
| **b** (소문자) | bit, 비트 | 속도 (Kbps, Mbps) |
| **B** (대문자) | Byte, 바이트 | 용량 (KB, MB) |

### 왜 이렇게 헷갈리게 만들었나

- 통신 분야는 전통적으로 **비트** 단위로 속도를 표기해왔습니다
- 저장 분야는 **바이트** 단위로 용량을 표기해왔습니다
- 서로 다른 분야의 관습이 만나면서 생긴 혼란입니다

### 실제로 계산할 때

```
   100 Mbps 회선

   1초에 보내는 비트 : 100,000,000 개
   1초에 보내는 바이트 : 100,000,000 ÷ 8 = 12,500,000 바이트
                       = 약 12.5 MB
```

> **즉, 100 Mbps 회선은 1초에 약 12.5 MB를 보냅니다.** "100 Mbps니까 1초에 100 MB"라고 생각하면 8배를 틀리게 됩니다.

### 변환 요령

```
   속도(bps) ÷ 8  =  초당 전송 바이트

   1 Mbps   →  약 0.125 MB/초
   8 Mbps   →  약 1 MB/초
   100 Mbps →  약 12.5 MB/초
   1 Gbps   →  약 125 MB/초
```

> **외우기 쉬운 기준** **8 Mbps = 1초에 1 MB** 이것만 기억하면 나머지는 비례로 계산할 수 있습니다.

## 5.3 직접 계산해보기

> 지금부터 실제 숫자를 넣어 계산해봅니다. 계산 자체가 목적이 아니라, **왜 새 방식이 필요한지**를 숫자로 확인하는 것이 목적입니다.

---

### 계산 1 — 10 MB를 CAN으로 보내면

**조건**

| 항목 | 값 |
| --- | --- |
| 보낼 데이터 | 10 MB |
| 통신 속도 | 500 Kbps |

**단순 계산 (이상적인 경우)**

```
   [1] 데이터를 비트로 환산
       10 MB = 10,000,000 바이트
             = 80,000,000 비트     (× 8)

   [2] 속도로 나누기
       80,000,000 ÷ 500,000 = 160초

   → 약 2분 40초
```

**그런데 실제로는 훨씬 오래 걸립니다.** 이유가 있습니다.

---

### 계산 2 — 실제로는 왜 더 걸리는가

**이유 ① : 덩어리마다 부가 정보가 붙는다**

4장에서 본 내용입니다.

```
   ┌────────┬──────────────┬────────┐
   │ 꼬리표  │   실제 내용   │ 검사값 │
   └────────┴──────────────┴────────┘
```

- CAN 한 덩어리는 8바이트인데, 그중 **1바이트는 순서 표시**에 씁니다
- 실제 데이터는 **7바이트**만 들어갑니다

```
   10 MB를 7바이트씩 나누면?

   10,000,000 ÷ 7 = 약 1,430,000 번
```

> **약 143만 번**을 나눠 보내야 합니다.

**이유 ② : 받는 쪽이 처리할 시간을 줘야 한다**

- 자동차 부품은 성능이 제한적입니다
- 계속 쏟아부으면 처리하지 못합니다
- 그래서 **"천천히 보내주세요"** 라고 요청합니다

```
   덩어리 하나 보내고 → 잠깐 대기 → 다음 덩어리
```

- 이 대기 시간이 1밀리초(0.001초)만 되어도

```
   1,430,000 번 × 0.001초 = 1,430초 = 약 24분
```

**종합**

| 조건 | 소요 시간 |
| --- | --- |
| 이상적 계산 | 약 3분 |
| 대기 시간 포함 | **약 30분** |
| 여기에 검증 시간 추가 | 더 길어짐 |

> **회선이 빨라도 받는 쪽이 못 따라오면 소용없습니다.** 이것이 CAN 방식의 근본적 한계입니다.

---

### 계산 3 — 같은 데이터를 이더넷으로 보내면

**조건**

| 항목 | 값 |
| --- | --- |
| 보낼 데이터 | 10 MB |
| 통신 속도 | 100 Mbps |
| 한 덩어리 크기 | 약 1,500 바이트 |

**계산**

```
   [1] 나누는 횟수
       10,000,000 ÷ 1,500 = 약 6,700 번

       (CAN의 143만 번과 비교 → 약 200분의 1)

   [2] 전송 시간
       10 MB ÷ 12.5 MB/초 = 0.8초
```

**결과**

| 방식 | 나누는 횟수 | 이론상 시간 |
| --- | --- | --- |
| CAN | 약 143만 번 | 약 3분 |
| 이더넷 | 약 6,700번 | **약 1초** |

---

### 계산 4 — 정리해서 비교하기

**10 MB 소프트웨어 전송 (실제 기준)**

| 방식 | 속도 | 실제 소요 시간 |
| --- | --- | --- |
| CAN | 500 Kbps | 약 30분 |
| CAN FD | 5 Mbps | 약 5분 |
| **이더넷 (DoIP)** | **100 Mbps** | **약 30초 ~ 1분** |

**차량 전체를 업데이트한다면 (부품 5개 기준)**

| 방식 | 소요 시간 |
| --- | --- |
| CAN | 약 2시간 30분 |
| 이더넷 | 약 5분 |

> 여기에 준비 작업과 검증 시간이 더 붙습니다. 실제 정비 현장에서의 차이는 이보다 더 벌어집니다.

## 5.4 이 계산이 의미하는 것

### 정비소 관점

```
   [CAN 방식]
   "소프트웨어 업데이트가 필요합니다. 한두 시간 걸립니다."
   → 고객은 차를 맡기고 가야 함

   [이더넷 방식]
   "소프트웨어 업데이트가 필요합니다. 몇 분이면 됩니다."
   → 고객이 기다렸다 바로 받아 감
```

| 항목 | 영향 |
| --- | --- |
| 고객 만족도 | 대기 시간 감소 |
| 정비소 수익 | 같은 시간에 더 많은 차량 처리 |
| 작업자 부담 | 대기 중 다른 작업 가능 |

### 생산 공장 관점

- 공장은 차량이 **정해진 시간 안에** 각 공정을 통과해야 합니다
- 이 시간을 넘기면 라인 전체가 멈춥니다

```
   차 1대당 소프트웨어 설치 시간

   30분  →  라인 정지, 생산 불가
    1분  →  정상 운영 가능
```

> 하루 수백~수천 대를 생산하는 공장에서 차 1대당 몇 분은 **생산량 차이**로 직결됩니다.

### 리콜 관점

```
   [상황] 소프트웨어 결함으로 10만 대 리콜

   차 1대당 2시간 → 총 20만 시간
   차 1대당 5분   → 총 8,300시간

   약 24배 차이
```

- 정비 인력 인건비, 대차 비용, 고객 불편 보상이 모두 여기에 비례합니다

### 그래서 업계가 이동하고 있습니다

```
   자동차 소프트웨어가 커졌다
             ↓
   기존 방식으로는 전송 시간이 감당 안 된다
             ↓
   더 넓은 통로가 필요하다
             ↓
   이미 검증된 인터넷 기술을 가져다 쓰자
             ↓
   그것이 DoIP
```

> **이것이 [4] DoIP 자료의 출발점입니다.** 지금 계산해본 숫자가 그 자료 전체의 배경입니다.

## 5장 정리

| 개념 | 핵심 |
| --- | --- |
| 용량 단위 | KB → MB → GB, 각 1,000배 |
| 속도 단위 | bps = 초당 비트 수 |
| **b와 B** | **8배 차이. 가장 흔한 실수 지점** |
| 변환 기준 | 8 Mbps = 1초에 1 MB |
| 실제 속도 | 이론값보다 훨씬 느림 (부가 정보 + 대기 시간) |
| 덩어리 크기 | 클수록 효율적 |

**한 장 요약**

```
   자동차 소프트웨어가 500배 커졌다
                 ↓
   그런데 통로 속도는 그대로였다
                 ↓
   8바이트씩 143만 번 나눠 보내야 한다
                 ↓
   실제로는 30분 이상 걸린다
                 ↓
   이더넷으로 바꾸면 1분 이내
                 ↓
   정비 시간, 생산량, 리콜 비용이 모두 여기에 달렸다
```

**기억할 숫자 하나**

```
   10 MB 전송

   CAN     : 약 30분
   이더넷  : 약 1분
```
