# (1) DoIP 개요

**1. DoIP 개요**

**1.1 DoIP 정의**

**정의**

- Diagnostics over Internet Protocol의 약자
- UDS 진단 메시지를 **TCP/IP 기반 이더넷으로 전송**하기 위한 프로토콜
- 국제 표준 **ISO 13400** 시리즈로 규격화
- CAN 환경의 ISO 15765(CAN TP)와 **동일한 위치**를 이더넷 환경에서 담당

**DoIP가 하는 일 / 하지 않는 일**

| 구분 | 담당 | 내용 |
| --- | --- | --- |
| 하지 않는 일 | UDS (ISO 14229) | 무엇을 진단할 것인가 — SID, DID, NRC 정의 |
| 하는 일 | DoIP (ISO 13400) | 어떻게 전달할 것인가 — 차량 탐색, 연결, 대상 ECU 지정, 캡슐화 |

- `22 F1 90`(VIN 읽기) 요청의 바이트 구성은 CAN이든 DoIP든 **완전히 동일**
- DoIP는 이를 IP 패킷에 담아 목적지 ECU까지 배달하는 역할만 수행
- → UDS 지식은 전송 방식이 바뀌어도 그대로 사용 가능

---

## 1.2 등장 배경

**ECU 소프트웨어 규모 급증**

- 과거 ECU 1개당 수십~수백 KB → 현재 도메인 컨트롤러는 수십 MB 이상
- 차량 1대당 ECU 수도 수십~100개 이상으로 증가

**현장 병목 발생**

- 생산 라인 : 차량 1대 플래싱 시간이 택트 타임 초과
- A/S : ECU 1개 업데이트에 수십 분~수 시간 소요

**인프라 및 서비스 환경 변화**

- ADAS·인포테인먼트용 이더넷 백본이 이미 구축됨 → 진단에 재활용 가능
- OTA 업데이트, 원격 진단 등 **IP 기반 서비스** 요구 대두
- 2011년 ISO 13400 제정, 현재 고속 진단의 표준으로 자리잡음

## 1.3 CAN 기반 진단의 한계

**(1) 대역폭 한계**

| 항목 | CAN | CAN FD | 차량용 이더넷 |
| --- | --- | --- | --- |
| 전송 속도 | 500 Kbps | 2~8 Mbps | 100 Mbps ~ 1 Gbps |
| 프레임당 데이터 | 8 byte | 최대 64 byte | 최대 1500 byte |
| 통신 방식 | 반이중 | 반이중 | 전이중 |

**(2) ISO-TP 오버헤드**

- 8 byte 초과 메시지는 ISO 15765-2가 여러 프레임으로 분할
- 각 프레임 첫 바이트를 PCI로 소비 → **8 byte 중 7 byte만 실 데이터**
- CAN 프레임 자체 헤더까지 포함하면 실효 처리율은 200~300 Kbps 수준

**(3) Flow Control에 의한 제약**

| 파라미터 | 의미 | 영향 |
| --- | --- | --- |
| STmin | CF 간 최소 전송 간격 | 클수록 속도 급락 |
| BS | FC 없이 연속 전송 가능한 CF 수 | 작을수록 왕복 증가 |

- ECU 성능이 낮을수록 큰 STmin 요구 → **회선이 빨라도 ECU가 못 따라오는 구조**
- STmin 1 ms만 되어도 실질 전송률은 약 7 KB/s로 제한

**(4) 전송 시간 예시**

- 10 MB 펌웨어 기준 : CAN 500 Kbps + STmin 1 ms → **약 30분**
- 동일 데이터를 100 Mbps 이더넷 전송 시 → **이론상 수 초**

**(5) 구조적 제약**

- 진단 대상 지정이 CAN ID에 종속 → ECU 증가 시 관리 부담
- 다수 ECU 동시 접근 어려움
- 재전송·순서 보장 기능이 전송 계층에 없음
- OBD-II 직접 연결 필수 → **원격 진단 불가**

> **정리** : 문제는 UDS의 기능 부족이 아니라 **파이프가 좁다는 것**  
> → 응용 계층은 그대로 두고 **전송 계층만 교체** → DoIP

## 1.4 DoIP 도입 효과

**성능**

- 대역폭 200~2000배 향상 → 플래싱 시간 수십 분 → 수 분 이하
- 페이로드 7 byte → 최대 1460 byte 수준, 오버헤드 대폭 감소
- 전이중 통신으로 요청/응답 동시 처리

**신뢰성 (TCP 활용)**

- 재전송, 순서 보장, 흐름 제어, 혼잡 제어를 TCP가 처리
- ISO-TP가 담당하던 기능을 검증된 표준 프로토콜에 위임

**확장성**

- **IP 주소 + 논리 주소(2 byte)** 2단계 주소 체계 → 최대 65,536개 ECU 지정 가능
- 하나의 연결로 여러 ECU 순차·병렬 진단 가능
- 게이트웨이 경유로 하위 CAN/LIN ECU까지 접근

**운용 편의성**

- 표준 소켓 API 기반 → 전용 하드웨어 없이 PC 이더넷 포트로 진단 가능
- Wireshark 등 범용 도구로 트래픽 분석 가능
- 원격 진단, OTA, 생산 라인 병렬 진단으로 활용 범위 확대

**트레이드오프**

| 항목 | 내용 |
| --- | --- |
| 보안 위협 증가 | IP 개방성으로 공격 표면 확대 → TLS·인증·접근 제어 필수 |
| 절차 복잡도 | 차량 탐색 → TCP 연결 → Routing Activation 필요 |
| 하드웨어 원가 | 이더넷 PHY, 스위치, 전용 배선 추가 |
| 타이밍 결정성 | TCP 재전송·혼잡 제어로 지연 변동 발생 |
| CAN 대체 불가 | 저가 ECU는 여전히 CAN 사용 → 게이트웨이가 중계 |

## 1.5 ISO 13400 시리즈 구성

| 규격 | 주요 내용 |
| --- | --- |
| **ISO 13400-1** | 전체 개요, 용어 정의, 유즈케이스 |
| **ISO 13400-2** | 메시지 구조, Payload Type, 연결 절차, 타이머 — **핵심 규격** |
| **ISO 13400-3** | 유선 이더넷 물리 계층, Activation Line, 커넥터 핀 할당 |
| **ISO 13400-4** | 고속 진단 전용 커넥터 규격 |

- 실제 통신 동작은 거의 전부 **Part 2**에 정의됨
- Part 3/4는 물리적 연결 방식(커넥터·배선)을 규정

## 1.6 프로토콜 스택 상의 위치

```
      [CAN 환경]                    [Ethernet 환경]

  ISO 14229 (UDS)               ISO 14229 (UDS)          L7 응용
         ↓                             ↓
  ISO 15765-2 (CAN TP)          ISO 13400-2 (DoIP)       L5~L4
         ↓                             ↓
         │                      TCP / UDP                L4 전송
         │                             ↓
         │                      IPv4 / IPv6              L3 네트워크
         ↓                             ↓
  ISO 11898 (CAN)               IEEE 802.3               L2/L1
                                100BASE-T1 / 1000BASE-T1
```

| 계층 | 담당 | 역할 |
| --- | --- | --- |
| 응용 | UDS | 진단 요청/응답 내용 생성 |
| DoIP | ISO 13400-2 | 차량 탐색, 연결 인가, 대상 ECU 지정, 헤더 캡슐화 |
| 전송 | TCP / UDP | 신뢰성 스트림(TCP), 브로드캐스트 탐색(UDP) |
| 네트워크 | IP | 주소 지정 및 라우팅 |
| 데이터링크/물리 | Ethernet | 실제 비트 전송 |

- UDS 계층은 두 환경에서 **동일**
- DoIP는 분할·재조립을 TCP에 위임한 대신, **차량 탐색과 접근 인가**라는 새 역할을 담당
- → 이것이 DoIP 연결 절차가 CAN보다 복잡한 이유

## 1.7 DoIP 통신의 기본 골격

**통신 주체**

| 주체 | 역할 |
| --- | --- |
| DoIP Tester | 진단을 수행하는 장비/소프트웨어 (진단기, PC, 진단 서버) |
| DoIP Entity | 차량 측 DoIP 처리 노드 (게이트웨이 또는 개별 ECU) |

**전송 계층 사용 구분**

| 프로토콜 | 포트 | 용도 |
| --- | --- | --- |
| UDP | 13400 | 차량 탐색, 차량 알림, 상태 조회 |
| TCP | 13400 | 진단 메시지, Routing Activation, Alive Check |
| TCP (TLS) | 3496 | 보안 적용 진단 메시지 |

- **UDP** : 상대를 모를 때 브로드캐스트로 찾는 단계
- **TCP** : 상대를 찾은 뒤 1:1 연결로 실제 데이터를 주고받는 단계

**통신 흐름 개요**

```
  [1] 물리 연결 및 IP 확보    케이블 연결 → Activation Line → IP 할당
  [2] 차량 탐색 (UDP)        브로드캐스트 → VIN/EID/GID/논리주소 응답
  [3] 연결 수립 (TCP)        TCP 소켓 연결
  [4] 접근 인가              Routing Activation 요청 → 승인/거부
  [5] 진단 메시지 교환        DoIP 헤더 + 논리주소 + UDS 데이터
  [6] 유지 및 종료           Alive Check → TCP 연결 종료
```

**메시지 캡슐화 구조**

```
  ┌──────────┬────┬─────┬─────────────┬─────────┬──────────┐
  │ Ethernet │ IP │ TCP │ DoIP Header │ Src/Tgt │ UDS Data │
  │  Header  │ Hdr│ Hdr │  (8 byte)   │ (4 byte)│  (가변)   │
  └──────────┴────┴─────┴─────────────┴─────────┴──────────┘
                        └── ISO 13400 ──┘        └ISO 14229┘
```

- 모든 DoIP 메시지는 **8 byte 공통 헤더**로 시작
- 진단 메시지는 헤더 뒤에 출발지/목적지 논리 주소 각 2 byte가 붙음
- UDS 데이터 부분은 CAN 진단과 **바이트 단위로 동일**
