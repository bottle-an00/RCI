# (8) DoIP 보안

**8. DoIP 보안**

**8.1 DoIP 환경의 보안 위협**

**CAN 진단 대비 위협 증가 요인**

| 요인 | 설명 |
| --- | --- |
| 원격 접근 가능 | 물리적 접근 없이 텔레매틱스 경유 진단 가능 → 공격 범위 확대 |
| 범용 기술 스택 | TCP/IP는 널리 알려진 기술 → 공격 도구·지식 접근성 높음 |
| 고대역폭 | 대량 데이터 탈취·주입이 짧은 시간에 가능 |
| 브로드캐스트 탐색 | 네트워크 내 차량 정보(VIN 등)가 요청 없이 노출될 수 있음 |
| 강력한 진단 권한 | 플래싱·설정 변경 등 차량 동작에 직접 영향 |

**주요 위협 유형**

| 위협 | 내용 |
| --- | --- |
| 무단 진단 접근 | 인가되지 않은 진단기가 연결하여 ECU 조작 |
| 도청 (Eavesdropping) | 평문 통신 구간에서 VIN·진단 데이터 탈취 |
| 중간자 공격 (MITM) | 진단기와 차량 사이에서 메시지 가로채기·변조 |
| 재전송 공격 (Replay) | 유효했던 인증 메시지를 재사용 |
| 서비스 거부 (DoS) | 다수 연결 요청으로 진단 소켓 자원 고갈 |
| 악성 펌웨어 주입 | 플래싱 경로를 통한 위·변조 SW 설치 |

**보안이 가장 중요한 구간**

- **플래싱(리프로그래밍)** — 차량 동작을 근본적으로 바꿀 수 있음
- **원격 진단 / OTA** — 물리 접근이라는 1차 방어선이 없음

## 8.2 다층 방어 구조

**계층별 보안 수단**

```
  ┌──────────────────────────────────────────┐
  │ [5] UDS 계층                              │
  │     SecurityAccess (0x27) / Authentication│  ← ECU 단위 권한
  ├──────────────────────────────────────────┤
  │ [4] DoIP 계층                             │
  │     Routing Activation 인증                │  ← 진단 경로 인가
  ├──────────────────────────────────────────┤
  │ [3] 전송 계층                              │
  │     TLS (포트 3496)                        │  ← 암호화·무결성
  ├──────────────────────────────────────────┤
  │ [2] 네트워크 계층                           │
  │     방화벽 / 접근 제어 (게이트웨이)           │  ← 트래픽 필터링
  ├──────────────────────────────────────────┤
  │ [1] 물리 계층                              │
  │     Activation Line / 물리적 접근           │  ← 1차 관문
  └──────────────────────────────────────────┘
```

**각 계층의 역할 구분**

| 계층 | 막는 대상 |
| --- | --- |
| 물리 | 인터페이스 자체를 열지 못하게 함 |
| 네트워크 | 허용되지 않은 트래픽 차단 |
| 전송(TLS) | 통신 내용의 도청·변조 방지 |
| DoIP | 인가되지 않은 진단 세션 개설 차단 |
| UDS | 특정 서비스 실행 권한 통제 |

- **어느 한 계층만으로는 불충분** — 계층별로 막는 위협이 다름
- 예: TLS는 도청을 막지만, 인증된 공격자의 오용은 막지 못함

## 8.3 TLS 적용

**기본 사항**

| 항목 | 내용 |
| --- | --- |
| 사용 포트 | **3496** (TCP, 평문은 13400) |
| 프로토콜 | TLS 1.2 이상 (1.3 권장) |
| 적용 범위 | TCP 기반 메시지 전체 (Routing Activation, 진단 메시지) |
| UDP 메시지 | **TLS 미적용** — 탐색 단계는 평문 |

**연결 흐름**

```
  [1] TCP 3-way handshake (포트 3496)
            ↓
  [2] TLS Handshake
       - 프로토콜 버전 / 암호 스위트 협상
       - 서버(차량) 인증서 검증
       - 클라이언트(진단기) 인증서 검증 (상호 인증 시)
       - 세션 키 생성
            ↓
  [3] 암호화 채널 확립
            ↓
  [4] Routing Activation → 진단 메시지 교환 (전 구간 암호화)
```

**TLS가 제공하는 것**

| 기능 | 효과 |
| --- | --- |
| 기밀성 (암호화) | 도청 시에도 내용 해독 불가 |
| 무결성 | 전송 중 변조 시 검출 |
| 인증 | 인증서로 상대방 신원 확인 |
| 재전송 방지 | 세션 키·순번으로 Replay 차단 |

**상호 인증 (Mutual TLS)**

- 차량뿐 아니라 **진단기도 인증서를 제시**하는 방식
- 정품 진단 장비만 접근을 허용하기 위해 사용
- 인증서 발급·갱신·폐기를 위한 **PKI 인프라**가 전제 조건

**차량 적용 시 제약**

| 제약 | 내용 |
| --- | --- |
| 연산 부하 | 암호 연산으로 ECU CPU 부담 증가 (HSM 활용으로 완화) |
| 핸드셰이크 지연 | 초기 연결에 수백 ms 추가 |
| 인증서 관리 | 차량 수명(10년 이상) 동안의 갱신·폐기 체계 필요 |
| 시각 동기 | 인증서 유효기간 검증에 정확한 시간 필요 |

**UDP 탐색 단계의 한계**

- Vehicle Announcement / Identification은 **평문 브로드캐스트**
- VIN 등 식별 정보가 네트워크에 노출될 수 있음
- 완화 방안 : VIN 대신 EID만 노출, 응답 범위 제한, 네트워크 분리

## 8.4 Routing Activation과 인증

**Routing Activation의 보안 역할**

- TCP 연결이 되어도 **진단 경로는 기본적으로 닫혀 있음**
- 인가 절차를 통과해야만 진단 메시지 전달 가능
- 5장에서 다룬 절차가 그대로 **접근 통제 지점** 역할

**보안 관련 Response Code**

| 코드 | 의미 | 보안 관점 |
| --- | --- | --- |
| 0x00 | 알 수 없는 Source Address | 등록되지 않은 진단기 차단 |
| 0x04 | **인증 필요 (미완료)** | 추가 인증 절차 요구 |
| 0x05 | 확인(Confirmation) 거부 | 사용자·차량 측 승인 필요 |
| 0x11 | 성공, 추가 확인 필요 | 조건부 승인 |

**Activation Type을 통한 권한 구분**

| Type | 용도 | 권한 수준 |
| --- | --- | --- |
| 0x00 | Default | 일반 진단 |
| 0x01 | WWH-OBD | 법규 대응 (제한적) |
| 0xE0 | **Central Security** | 보안 인증 경로 |

- Activation Type에 따라 **접근 가능한 ECU·서비스 범위를 제한**하는 설계가 일반적
- 예: Default로는 읽기만, 플래싱은 별도 Type + 인증 요구

**Further Action Required (탐색 단계)**

| 값 | 의미 |
| --- | --- |
| 0x00 | 추가 조치 불필요 |
| **0x10** | **중앙 보안 인증 필요** |

- 탐색 응답 단계에서 이미 "인증이 필요한 차량"임을 통보
- 진단기는 이를 확인하고 인증 절차를 준비

## 8.5 UDS 계층 보안

**SecurityAccess (0x27)**

- Seed-Key 방식의 전통적 인증

```
  진단기 → ECU : 27 01           (Seed 요청)
  ECU → 진단기 : 67 01 [Seed]    (난수 전달)
  진단기 → ECU : 27 02 [Key]     (알고리즘 연산 결과)
  ECU → 진단기 : 67 02           (인증 성공)
```

| 한계 | 내용 |
| --- | --- |
| 대칭 키 공유 | 알고리즘·키가 진단기에 존재 → 유출 시 전체 무력화 |
| 재전송 취약 | Seed 난수성이 약하면 Replay 가능 |
| 확장성 부족 | 키 갱신·폐기 체계가 사실상 없음 |

**Authentication (0x29)**

- 인증서 기반의 강화된 인증 서비스
- PKI 기반 공개키 방식 → 대칭 키 유출 위험 해소
- 역할(Role) 기반으로 권한 세분화 가능
- 원격 진단·OTA 환경에서 채택 확대

| 구분 | 0x27 SecurityAccess | 0x29 Authentication |
| --- | --- | --- |
| 방식 | Seed-Key (대칭) | 인증서 (비대칭) |
| 키 관리 | ECU·진단기에 사전 배포 | PKI로 발급·폐기 |
| 권한 구분 | 레벨 단위 | 역할 단위 세분화 |
| 원격 적합성 | 낮음 | 높음 |

**DoIP 계층 인증과의 차이**

| 구분 | Routing Activation 인증 | UDS 0x27 / 0x29 |
| --- | --- | --- |
| 통제 대상 | **진단 연결 전체** | **개별 ECU의 서비스** |
| 시점 | 연결 수립 시 1회 | 서비스 실행 전 |
| 실패 시 | 진단 메시지 자체 불가 | 해당 서비스만 거부(NRC 0x33) |

- 두 인증은 **중첩 적용**되며 대체 관계가 아님

## 8.6 게이트웨이 접근 제어

**게이트웨이의 보안 관문 역할**

```
        [외부 진단기 / TCU]
              │
              ▼
   ┌──────────────────────┐
   │   중앙 게이트웨이      │
   │  ┌────────────────┐  │
   │  │ 방화벽 / 필터링  │  │  ← 포트·프로토콜 제한
   │  ├────────────────┤  │
   │  │ 연결 수 제한     │  │  ← DoS 완화
   │  ├────────────────┤  │
   │  │ 주소 화이트리스트 │  │  ← 접근 가능 ECU 제한
   │  ├────────────────┤  │
   │  │ IDS 로깅         │  │  ← 이상 징후 탐지
   │  └────────────────┘  │
   └──────────┬───────────┘
              ▼
        [내부 ECU들]
```

**주요 제어 항목**

| 항목 | 내용 |
| --- | --- |
| 포트 제한 | 13400 / 3496 외 차단 |
| 연결 수 제한 | 최대 동시 소켓 수 제한으로 자원 고갈 방지 |
| Target Address 필터 | 외부에서 접근 가능한 ECU를 화이트리스트로 관리 |
| 서비스 필터 | 특정 SID(플래싱 계열)를 조건부로만 허용 |
| 네트워크 분리 | 진단용 VLAN 분리, 도메인 간 라우팅 제한 |

**차량 상태 기반 제어**

| 조건 | 제한 내용 |
| --- | --- |
| 주행 중 | 플래싱·설정 변경 서비스 차단 |
| 시동 OFF | 배터리 방전 방지를 위한 연결 시간 제한 |
| 슬립 모드 | 진단 인터페이스 비활성 |

- UDS의 NRC **0x22 (conditionsNotCorrect)** 로 거부 응답
- 안전(Safety)과 보안(Security)이 함께 고려되는 지점

**침입 탐지 및 로깅**

| 기록 대상 | 활용 |
| --- | --- |
| Routing Activation 실패 이력 | 반복 시도 = 공격 징후 |
| 비정상 Target Address 접근 | 스캐닝 시도 탐지 |
| 예상치 못한 시점의 플래싱 요청 | 악성 SW 주입 시도 |

- 차량 IDS(Intrusion Detection System)와 연계하여 백엔드로 보고

## 8.7 원격 진단 환경의 추가 고려

**유선 대비 취약해지는 점**

| 항목 | 유선 | 원격 |
| --- | --- | --- |
| 물리 접근 방어 | 있음 (Activation Line) | **없음** |
| 공격자 위치 | 차량 근처 필수 | 어디서든 가능 |
| 필수 보안 수단 | 선택적 | **TLS·인증 필수** |

**요구되는 보안 요소**

- **종단 간 암호화** : 백엔드 서버 ↔ 차량 전 구간
- **강한 상호 인증** : 서버·차량 양측 인증서 검증
- **작업 승인 절차** : 중요 작업 시 차량 소유자 동의
- **롤백 대비** : 플래싱 실패 시 복구 이미지 유지
- **서명 검증** : 펌웨어 이미지의 디지털 서명 확인 후 적용

**OTA 플래싱 보안 흐름 예시**

```
  [1] 백엔드 ↔ 차량 상호 인증 (TLS + 인증서)
  [2] 펌웨어 이미지 다운로드 (암호화 전송)
  [3] 차량 내에서 서명 검증 (변조 여부 확인)
  [4] 차량 상태 확인 (주차·전원·배터리)
  [5] 사용자 동의 획득
  [6] DoIP 경로로 대상 ECU 플래싱
  [7] 검증(CRC/서명) 후 활성화, 실패 시 롤백
```

## 8.8 관련 표준 및 규제

| 항목 | 내용 |
| --- | --- |
| **UN R155** | 차량 사이버보안 관리체계(CSMS) 요구. 형식승인 필수 |
| **UN R156** | SW 업데이트 관리체계(SUMS). OTA 관련 요건 |
| **ISO/SAE 21434** | 차량 사이버보안 엔지니어링 프로세스 표준 |
| **ISO 14229-1 (0x29)** | Authentication 서비스 정의 |

- **UN R155/R156은 권고가 아닌 법규** — 미충족 시 판매 불가
- 따라서 DoIP 보안은 선택 사항이 아니라 **양산 요구 조건**
