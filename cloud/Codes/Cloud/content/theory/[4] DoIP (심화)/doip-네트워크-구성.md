# (3) DoIP 네트워크 구성

## **3. DoIP 네트워크 구성**

#### 3.1 통신 주체 정의

**DoIP Tester (Client)**

- 진단을 요청하는 주체
- 형태 : 외부 진단 장비, PC 진단 소프트웨어, 원격 진단 서버, 생산 라인 장비
- 역할
  - 차량 탐색 요청 송신
  - TCP 연결 및 Routing Activation 요청
  - UDS 요청 생성 및 응답 해석

**DoIP Entity (Server)**

- 차량 측에서 DoIP 프로토콜을 처리하는 노드
- 진단기의 요청을 수신하고 응답하거나, 하위 ECU로 중계
- 차량 1대에 여러 Entity가 존재할 수 있음

**DoIP Entity의 3가지 유형**

| 유형 | 역할 | 특징 |
| --- | --- | --- |
| **DoIP Node** | 자기 자신에 대한 진단만 처리 | 이더넷에 직접 연결된 개별 ECU |
| **DoIP Gateway** | 자신 + 하위 네트워크 ECU 중계 | 논리 주소 ↔ CAN ID 변환 수행 |
| **DoIP Edge Node** | 차량 외부와의 접점, 네트워크 경계 담당 | 외부 진단기가 처음 만나는 노드 |

**Edge Node의 특별한 역할**

- 차량 외부에서 접근할 때 **가장 먼저 접촉하는 관문**
- 차량 전체를 대표하여 VIN, GID, EID 정보를 응답
- 외부 진단기 연결 수를 관리하고 접근 통제 수행
- 실제 차량에서는 **중앙 게이트웨이(CGW)가 Edge Node 역할을 겸하는 경우가 대부분**

---

#### 3.2 네트워크 구성 형태

**전형적인 차량 구조**

```
   [외부 진단기]
        │ OBD-II (Ethernet)
        ▼
  ┌──────────────────────────┐
  │  중앙 게이트웨이 (CGW)     │  ← Edge Node + Gateway
  │  Logical Address: 0x0E00 │
  └───┬──────────────────┬───┘
      │ Ethernet         │ CAN
      ▼                  ▼
 ┌──────────┐      ┌──────────┐
 │ ADAS ECU │      │ 엔진 ECU  │
 │  0x0E10  │      │  0x0E80  │
 └──────────┘      └──────────┘
 ┌──────────┐      ┌──────────┐
 │ 인포테인먼트│      │ 브레이크  │
 │  0x0E11  │      │  0x0E81  │
 └──────────┘      └──────────┘
   (DoIP Node)      (CAN ECU, 게이트웨이가 중계)
```

**진단기 관점의 동작**

- 진단기는 게이트웨이 IP 하나에만 TCP 연결
- 목적지 논리 주소만 바꿔가며 여러 ECU 진단 가능
- 대상이 이더넷 ECU인지 CAN ECU인지 **진단기는 구분할 필요 없음**
- 게이트웨이가 주소를 보고 알아서 경로 결정

**게이트웨이의 중계 처리**

| 대상 | 게이트웨이 동작 |
| --- | --- |
| 이더넷 ECU | DoIP 메시지를 해당 ECU IP로 전달 |
| CAN ECU | 논리 주소를 CAN 진단 ID로 변환 → ISO-TP로 전송 |
| 자기 자신 | 내부 진단 스택으로 직접 처리 |

- CAN 구간은 여전히 느리므로, **CAN ECU 진단 속도는 개선되지 않음**
- DoIP의 속도 이점은 이더넷에 직접 연결된 ECU에서만 온전히 발휘됨

#### 3.3 논리 주소 (Logical Address)

**논리 주소란**

- DoIP 네트워크 내에서 **진단 대상을 식별하는 2 byte(16 bit) 주소**
- IP 주소가 "어느 차량/노드인가"라면, 논리 주소는 "그 안의 어느 진단 대상인가"
- CAN 진단의 진단 요청/응답 CAN ID에 대응하는 개념

**2단계 주소 체계**

```
   IP 주소 192.168.0.10  ← 어느 게이트웨이인가
            +
   논리 주소 0x0E80       ← 그 뒤의 어느 ECU인가
            ↓
   최종 진단 대상 결정
```

**주소 범위 (ISO 13400-2 규정)**

| 범위 | 용도 |
| --- | --- |
| 0x0000 | 예약 (사용 불가) |
| 0x0001 ~ 0x0DFF | 차량 제조사 정의 (VM specific) |
| 0x0E00 ~ 0x0FFF | **외부 진단기(Tester)** 용 |
| 0x1000 ~ 0x7FFF | 차량 제조사 정의 (ECU) |
| 0x8000 ~ 0xCFFF | 예약 |
| 0xE000 ~ 0xE3FF | 기능 주소(Functional) 그룹 |
| 0xE400 ~ 0xEFFF | 차량 제조사 정의 기능 주소 |
| 0xF000 ~ 0xFFFF | 예약 / 시스템용 |

- 실제 값 할당은 **완성차 업체별 규격**을 따르므로, 프로젝트 문서 확인이 필수
- 위 표는 표준이 정한 큰 틀

**Source / Target Address**

- 모든 진단 메시지에는 출발지·목적지 주소가 각각 포함됨

| 필드 | 크기 | 내용 |
| --- | --- | --- |
| Source Address (SA) | 2 byte | 송신자 주소 (진단기 주소) |
| Target Address (TA) | 2 byte | 수신자 주소 (대상 ECU) |

- 진단기 주소는 Routing Activation 시점에 등록되며, 이후 모든 메시지에서 동일하게 사용
- 게이트웨이는 등록되지 않은 SA의 메시지를 거부함

**물리 주소 vs 기능 주소**

| 구분 | 대상 | 용도 |
| --- | --- | --- |
| 물리 주소 (Physical) | 특정 ECU 1개 | 일반적인 진단, 플래싱 |
| 기능 주소 (Functional) | 여러 ECU 동시 | 세션 전환, TesterPresent 브로드캐스트 |

- 기능 주소 사용 시 여러 ECU가 각각 응답할 수 있음
- 게이트웨이가 해당 그룹의 모든 ECU에 메시지를 복제 전송

#### 3.4 차량 식별 정보

DoIP 탐색 단계에서 차량은 자신을 식별하는 3가지 정보를 응답한다.

| 정보 | 크기 | 내용 |
| --- | --- | --- |
| **VIN** | 17 byte | 차대번호. 차량을 고유하게 식별 |
| **EID** | 6 byte | Entity ID. 보통 해당 노드의 MAC 주소 사용 |
| **GID** | 6 byte | Group ID. 같은 차량에 속한 Entity들의 그룹 식별자 |

**각 정보의 용도**

- **VIN** : 진단기가 "어떤 차량인지" 확인. 생산 라인에서 다수 차량 중 대상 선별에 사용
- **EID** : VIN이 아직 기록되지 않은 신차·개발 차량 식별에 사용
- **GID** : 여러 Entity가 응답할 때 **같은 차량 소속인지 판별**

**VIN 미기록 상태 처리**

- 생산 초기 단계에서는 VIN이 아직 쓰이지 않은 경우가 있음
- 이때 VIN 필드는 0x00 또는 0xFF로 채워짐
- 진단기는 VIN 대신 **EID(MAC 주소)로 차량을 식별**

#### 3.5 연결 관리

**동시 연결 제한**

- DoIP Entity는 동시에 수용 가능한 TCP 연결 수가 제한됨 (구현별 상이, 통상 1~수 개)
- 최대치 도달 시 신규 연결 요청은 거부되거나, 가장 오래된 연결이 해제됨

**연결 상태 구분**

| 상태 | 설명 |
| --- | --- |
| Socket Initialized | TCP 연결은 되었으나 Routing Activation 전 |
| Registered / Activated | Routing Activation 완료, 진단 메시지 교환 가능 |
| Closed | 연결 종료 |

- **TCP 연결만으로는 진단 불가** — 반드시 Routing Activation을 거쳐야 함
- 이는 무단 접근을 막기 위한 1차 관문 역할

**연결 유지 및 해제 조건**

| 조건 | 동작 |
| --- | --- |
| 일정 시간 무통신 | Inactivity 타이머 만료 → 연결 해제 |
| Alive Check 무응답 | 연결 비정상 판단 → 해제 |
| 케이블 분리 / 링크 다운 | 즉시 연결 해제 |
| 진단기의 정상 종료 | TCP FIN으로 정상 해제 |

**여러 진단기의 동시 접속**

- 복수 진단기 접속을 허용하는 Entity도 존재
- 단, 동일 ECU에 대한 동시 진단은 충돌 위험이 있어 제한하는 것이 일반적
- 플래싱 등 배타적 작업 중에는 다른 연결을 거부하도록 설계
