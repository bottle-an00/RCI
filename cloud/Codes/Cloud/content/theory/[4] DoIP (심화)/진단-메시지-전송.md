# (7) 진단 메시지 전송

## **7. 진단 메시지 전송**

#### 7.1 Diagnostic Message (0x8001)

**정의**

- UDS 요청/응답을 실제로 실어 나르는 메시지
- 진단기 → 차량, 차량 → 진단기 **양방향 모두 동일한 Payload Type 사용**
- Routing Activation이 완료된 TCP 연결에서만 송수신 가능

**구조**

```
  ┌──────────────────────┬──────────┬──────────┬────────────┐
  │   Generic Header     │  Source  │  Target  │  UDS Data  │
  │      (8 byte)        │  (2byte) │  (2byte) │   (가변)    │
  └──────────────────────┴──────────┴──────────┴────────────┘
                          └── DoIP 라우팅 정보 ─┘ └ ISO 14229 ┘
```

**방향별 주소 사용**

| 방향 | Source Address | Target Address |
| --- | --- | --- |
| 요청 (진단기 → ECU) | 진단기 주소 (예: 0x0E00) | 대상 ECU 주소 (예: 0x0E80) |
| 응답 (ECU → 진단기) | ECU 주소 (0x0E80) | 진단기 주소 (0x0E00) |

- 응답에서는 **SA와 TA가 서로 뒤바뀜**
- 진단기는 이를 통해 어느 ECU가 보낸 응답인지 판별

**UDS Data 영역**

- CAN 진단에서 사용하던 것과 **바이트 단위로 완전히 동일**
- ISO-TP의 PCI 바이트(SF/FF/CF)가 **존재하지 않음**
- 길이 제한이 사실상 없음 → 대용량 데이터를 한 번에 전송 가능

| 구분 | CAN (ISO-TP) | DoIP |
| --- | --- | --- |
| 데이터 앞 부가 정보 | PCI 1~2 byte | 없음 |
| 최대 길이 | 4095 byte (표준 TP) | 수 MB 이상 |
| 분할 처리 | 응용에서 인지 필요 | TCP가 투명하게 처리 |

#### 7.2 ACK / NACK 메커니즘

**2단계 응답 구조**

DoIP 진단 메시지는 **응답이 두 번 온다**는 점이 CAN과의 큰 차이다.

```
  [진단기]                              [차량]

  Diagnostic Message (0x8001)
  22 F1 90              ─────────────→
                                        [1] DoIP 계층 수신 확인
                        ←─────────────
  Diagnostic ACK (0x8002)                ← 1차 응답 (전달 확인)

                                        [2] UDS 계층 서비스 처리
                        ←─────────────
  Diagnostic Message (0x8001)            ← 2차 응답 (진단 결과)
  62 F1 90 ...
```

**두 응답의 의미 구분**

| 응답 | 계층 | 의미 |
| --- | --- | --- |
| **Positive ACK (0x8002)** | DoIP | "메시지를 잘 받아서 ECU로 전달했다" |
| **Diagnostic Message (0x8001)** | UDS | "진단 서비스를 처리한 결과는 이렇다" |

- **ACK는 진단 결과가 아님** — 단순 전달 확인
- ACK를 받았다고 진단이 성공한 것이 아니며, 이후 UDS 응답을 기다려야 함
- 반대로 NACK를 받으면 UDS 응답은 **오지 않음**

**Diagnostic Message Positive ACK (0x8002)**

| 필드 | 크기 | 내용 |
| --- | --- | --- |
| Source Address | 2 byte | ACK 송신 노드 |
| Target Address | 2 byte | 원 요청자 |
| ACK Code | 1 byte | 0x00 (고정) |
| Previous Message | 가변 | 원본 메시지 일부 (선택) |

**Diagnostic Message Negative ACK (0x8003)**

| 필드 | 크기 | 내용 |
| --- | --- | --- |
| Source Address | 2 byte | NACK 송신 노드 |
| Target Address | 2 byte | 원 요청자 |
| NACK Code | 1 byte | 오류 코드 |
| Previous Message | 가변 | 원본 메시지 일부 (선택) |

**NACK Code 목록**

| 코드 | 의미 | 원인 |
| --- | --- | --- |
| 0x02 | Invalid Source Address | SA가 등록된 값과 다름 |
| 0x03 | Unknown Target Address | 존재하지 않는 대상 ECU |
| 0x04 | Diagnostic Message Too Large | 수신측 처리 한계 초과 |
| 0x05 | Out of Memory | 자원 부족 |
| 0x06 | Target Unreachable | 대상 ECU 응답 없음 (하위 네트워크 문제) |
| 0x07 | Unknown Network | 알 수 없는 하위 네트워크 |
| 0x08 | Transport Protocol Error | 하위 TP 전송 실패 (예: CAN 구간 오류) |

**NACK 코드별 점검 방향**

| 코드 | 확인 사항 |
| --- | --- |
| 0x02 | Routing Activation 시 등록한 SA와 일치하는가 |
| 0x03 | 대상 ECU 논리 주소가 차량 규격과 맞는가 |
| 0x06 / 0x08 | 게이트웨이 하위 CAN 구간 상태, ECU 전원·슬립 여부 |

#### 7.3 UDS 서비스 매핑

**동일하게 동작하는 부분**

- SID, Sub-function, DID, 파라미터 구성 → **변경 없음**
- Positive Response (SID + 0x40), Negative Response (0x7F) → 동일
- 세션, SecurityAccess 개념 → 동일

**요청/응답 예시 비교**

| 항목 | CAN 진단 | DoIP 진단 |
| --- | --- | --- |
| 요청 | `[PCI] 22 F1 90` | `[DoIP Header][0E00][0E80] 22 F1 90` |
| 응답 | `[PCI] 62 F1 90 ...` | `[DoIP Header][0E80][0E00] 62 F1 90 ...` |
| 대상 지정 | 진단 요청 CAN ID | Target Address (2 byte) |

**주요 서비스별 DoIP 환경 특성**

| SID | 서비스 | DoIP에서의 특징 |
| --- | --- | --- |
| 0x10 | DiagnosticSessionControl | 동일. 응답의 P2 값은 DoIP 환경에 맞게 설정 |
| 0x3E | TesterPresent | **여전히 필요** (Alive Check와 별개) |
| 0x22 | ReadDataByIdentifier | 대용량 DID를 한 번에 읽기 유리 |
| 0x34 | RequestDownload | **maxNumberOfBlockLength가 크게 증가** |
| 0x36 | TransferData | 블록 크기 확대로 반복 횟수 대폭 감소 |
| 0x19 | ReadDTCInformation | 대량 DTC를 한 번에 수신 가능 |

**RequestDownload의 변화**

```
  [CAN 환경]
   maxNumberOfBlockLength ≈ 수백 ~ 4095 byte
   10 MB 전송 → TransferData 수천 회 반복

  [DoIP 환경]
   maxNumberOfBlockLength ≈ 수 KB ~ 수십 KB 이상
   10 MB 전송 → TransferData 수백 회 이하
```

- 블록 크기 확대가 **플래싱 시간 단축의 실질적 원인**
- 단, ECU의 플래시 쓰기 속도와 RAM 버퍼 크기가 새로운 상한이 됨

**기능 주소(Functional) 사용 시**

- 진단기가 Target Address에 기능 주소 그룹 값을 지정
- 게이트웨이가 해당 그룹의 모든 ECU에 메시지 복제 전송
- **여러 ECU가 각각 응답**하므로, 진단기는 SA로 구분하여 수집
- 주로 `0x3E TesterPresent`, `0x10 DiagnosticSessionControl` 브로드캐스트에 사용

#### 7.4 타이밍 파라미터

**UDS 레벨 타이머 (변경 없음)**

| 타이머 | 의미 | 비고 |
| --- | --- | --- |
| **P2 Server** | ECU 응답 최대 시간 | 통상 50 ms |
| **P2\* Server** | NRC 0x78 이후 연장된 응답 시간 | 통상 5000 ms |
| **S3 Server** | 세션 유지 타이머 | 통상 5000 ms |

- P2/P2\* 값은 `0x10` 응답에 포함되어 전달됨
- **NRC 0x78 (ResponsePending)** 동작 방식도 CAN과 동일

**DoIP 레벨 타이머**

| 타이머 | 대략 값 | 용도 |
| --- | --- | --- |
| **A\_DoIP\_Diagnostic\_Message** | 2 s | ACK/NACK 수신 대기 |
| **A\_DoIP\_Ctrl** | 2 s | 제어 메시지 응답 대기 |
| **T\_TCP\_General\_Inactivity** | 5 s | 무통신 시 연결 해제 |
| **T\_TCP\_Alive\_Check** | 500 ms | Alive Check 응답 대기 |

**타이머 적용 구간**

```
  요청 송신
     │
     ├─ A_DoIP_Diagnostic_Message (2s) ─→ ACK/NACK 수신
     │
     └─ P2 Server (50ms) ────────────────→ UDS 응답 수신
             │
             └─ NRC 0x78 수신 시
                  └─ P2* Server (5000ms) → 최종 응답 수신
```

**주의 : 타이머 중복 관리**

- DoIP 타이머와 UDS 타이머는 **동시에 동작**
- ACK는 왔는데 UDS 응답이 없다면 → **ECU 또는 하위 네트워크 문제**
- ACK 자체가 없다면 → **DoIP 계층 또는 연결 문제**
- 이 구분이 장애 원인 파악의 출발점

#### 7.5 대용량 데이터 전송

**플래싱 시나리오에서의 흐름**

```
  0x10 02        Programming Session 진입
       ↓
  0x27           SecurityAccess 인증
       ↓
  0x34           RequestDownload
                 → 응답에 maxNumberOfBlockLength 포함
       ↓
  0x36 (반복)     TransferData — 블록 단위 전송
       ↓
  0x37           RequestTransferExit
       ↓
  0x31           RoutineControl (검증 / CRC 확인)
       ↓
  0x11 01        ECUReset
```

**DoIP 환경의 병목 이동**

| 구간 | CAN 환경 | DoIP 환경 |
| --- | --- | --- |
| 네트워크 전송 | **주 병목** | 거의 무시 가능 |
| ECU 플래시 쓰기 | 상대적으로 여유 | **새로운 병목** |
| ECU RAM 버퍼 | 영향 적음 | 블록 크기 상한 결정 |

- 회선 속도가 개선되면서 **ECU 자체 처리 능력이 성능을 좌우**
- 따라서 블록 크기를 무작정 키워도 효과가 없을 수 있음

**전송 중 유의 사항**

| 항목 | 내용 |
| --- | --- |
| TesterPresent 유지 | 플래싱 중에도 세션 유지 필요 (기능 주소 활용) |
| Alive Check 응답 | 대용량 전송 중에도 즉시 응답해야 연결 유지 |
| NRC 0x78 처리 | 플래시 소거 중 다수 발생 → P2\* 대기 필수 |
| 전원 안정성 | 전송 시간 단축으로 위험은 감소했으나 여전히 필수 |

#### 7.6 오류 상황 진단 가이드

**증상별 원인 분류**

| 증상 | 추정 원인 | 확인 위치 |
| --- | --- | --- |
| Routing Activation 실패 (0x00) | SA 값 불일치 | 진단기 설정 |
| Routing Activation 실패 (0x01) | 동시 연결 초과 | Entity Status 조회 |
| Diagnostic NACK 0x02 | 등록되지 않은 SA로 송신 | Routing Activation 이력 |
| Diagnostic NACK 0x03 | 잘못된 Target Address | 차량 논리 주소 규격 |
| Diagnostic NACK 0x06 / 0x08 | 하위 CAN 구간 문제 | ECU 전원, CAN 버스 상태 |
| ACK는 오는데 UDS 응답 없음 | ECU 처리 지연 또는 정지 | ECU 상태, P2\* 설정 |
| 연결이 자꾸 끊김 | Alive Check 미응답 / Inactivity | 진단기 응답 처리 로직 |
| 헤더 NACK 0x00 / 0x04 | 프로토콜 버전·길이 오류 | 진단기 구현 |

**계층별 문제 절단 방법**

```
  ping 응답 없음        → 물리/IP 계층 (4장 참조)
        ↓ 정상
  UDP 탐색 응답 없음    → 방화벽, 브로드캐스트 도달 여부
        ↓ 정상
  TCP 연결 실패        → 포트 13400, 동시 연결 수
        ↓ 정상
  Routing Act. 실패    → SA / Activation Type / 인증
        ↓ 정상
  Diagnostic NACK      → Target Address / 하위 네트워크
        ↓ 정상
  UDS NRC 응답         → ECU 세션·보안·조건 (UDS 영역)
```

- **아래로 갈수록 UDS 문제**, **위로 갈수록 네트워크 문제**
- 이 순서대로 절단해 나가면 원인 범위를 빠르게 좁힐 수 있음
