# miniGIT UR3(로봇팔) 클라우드(웹 진단 앱) 기능개발 요청서

*Development Request — Cloud / Web Diagnostic App for UR3*

- 문서번호: MINIGIT-REQ-CLOUD-UR-001
- 버전: 0.1
- 작성일: 2026-07-29
- 분류: 학습용 (내부)
- 요청 주체: RCI/UR3 개발 담당
- 수신 대상: 클라우드(웹 진단 앱) 개발 담당
- 관련 문서: UR3 진단 통신 사양서, UR3 RCI 기능명세서, UR3(로봇) 기능명세서 (모두 작성 예정)

> 본 문서는 클라우드(웹 진단 앱) 담당자가 개발에 착수할 수 있도록 알아야 할 모든 인터페이스, 프로토콜, 책임 범위를 정리한 요청서다. 웹 진단 앱은 실제 제품의 GDS-SMART 앱을 대체하며, MQTT를 통해 RCI(게이트웨이)와 통신한다.

## 1. 배경 및 전체 구조

```
[웹 진단 앱(클라우드)] ──MQTT──▶ [RCI(RSP4)] ──RTDE/Dashboard/RTDEControl──▶ [UR3 Control Box + UR3 로봇팔]
      GDS-SMART 대체              VCI 장치 + 진단 에이전트         텔레메트리 읽기/제어 대상
      └────────── MQTT 응답 ◀──── UDS 응답 조립 ◀──── RTDE/Dashboard 응답 ◀──────┘
```

- 웹앱 ↔ RCI: MQTT (블루투스 대체)
- RCI ↔ UR3 Control Box: RTDE(텔레메트리 읽기) / Dashboard(프로그램, 전원, 안전 제어) / RTDEControlInterface(모션 제어)
- RC카 세트에서는 RCI가 CAN 바이트를 그대로 중계하고 UDS 요청을 실제로 해석하고 처리하는 것은 RC카(ECU) 쪽이었다. UR 컨트롤박스는 자체 UDS 서버를 갖고 있지 않고 RTDE/Dashboard/URScript라는 표준 인터페이스만 제공하므로, UR3 세트에서는 RCI가 UDS 서버(진단 에이전트) 역할을 직접 수행한다 — 요청 해석, 세션/보안/DTC 상태 관리, UR3에 대한 실제 제어 실행, 응답 조립까지 RCI 안에서 이루어진다. RC카 세트는 RSP5라는 별도의 프로그래밍 가능한 보드에 UDS 서버 소프트웨어를 둘 수 있었지만, UR3 세트에는 그런 자리가 RCI(라즈베리파이 4) 뿐이라 RCI가 이 역할까지 맡는다.

### 용어

| 용어 | 설명 |
|---|---|
| 텔레메트리 (Telemetry) | RTDE(Real-Time Data Exchange, TCP 30004)로 UR 컨트롤박스에서 주기 수신하는 로봇 상태 데이터(관절각, 속도, 전류, TCP 자세, robot_mode, safety_mode 등). RCI는 이를 읽기 전용으로 구독해 최신값 캐시를 유지한다 |
| Dashboard | UR 컨트롤박스가 제공하는 TCP 29999 텍스트 명령 인터페이스. 프로그램 재생/정지/일시정지, 전원 on/off, 브레이크 해제, 안전 복구 등 사전 정의된 동작을 수행한다 |
| RTDEControlInterface | ur_rtde 라이브러리가 제공하는 로봇 제어 채널. `moveJ`/`moveL` 같은 모션 명령과 `stopJ`/`stopL` 정지를 수행한다(§5.6 참조) |
| LWT (Last Will and Testament) | MQTT 클라이언트가 접속 시 브로커에 미리 등록해두는 유언 메시지. 클라이언트가 정상적으로 접속을 끊지 않고 비정상 종료되면 브로커가 대신 이 메시지를 발행한다. RCI는 이를 이용해 비정상 종료 시 상태 토픽에 offline을 자동으로 알린다(§3 참조) |

### 1.1 역할 분담

| 작업 | 담당 | 설명 |
|---|---|---|
| UI/화면 | 클라우드 | 진단/모션 요청 버튼, 입력, 결과 표시 |
| UI 조작 → UDS 요청 바이트 조립 | 클라우드 | 예: "관절 각도 읽기" 버튼 → `"22 01 01"` |
| MQTT 발행/구독 | 클라우드 | §3 토픽/페이로드 |
| MQTT 수신 → UDS 해석, 세션/보안/DTC 상태 관리, 응답 생성 | RCI | RC카 세트와 달리 RCI가 이 역할을 직접 수행 |
| UR3 데이터 취득(RTDE) 및 제어(Dashboard/RTDEControlInterface) 실행 | RCI | UR 컨트롤박스와 통신, 실제 로봇 구동 |
| 응답 raw 바이트 → 물리값 디코딩 | 클라우드 | 예: `62 01 01 FC 7C ...` → 관절각 -90.0도 등 |
| NRC 바이트 → 이름/메시지 매핑 | 클라우드 | 예: `31` → requestOutOfRange |

클라우드는 RC카 세트와 동일하게 UDS 프로토콜(요청 조립 + 응답 디코딩)의 주체이지만, 그 요청을 실제로 처리하는 주체가 RC카 세트에서는 별도의 ECU였던 반면 UR3 세트에서는 RCI 자신이라는 점이 다르다. 본 문서 §5의 프로토콜 표가 그 사양이다.

## 2. 클라우드 담당 기능요구사항 (요약)

| # | 기능 | 설명 |
|---|---|---|
| CR1 | MQTT 브로커 호스팅 | 브로커는 클라우드에 둔다. 접속 정보(호스트/포트/자격증명/TLS)를 RCI 담당에게 제공 |
| CR2 | 직접 코딩(Raw UDS 메시지 작성) — 핵심 인터페이스 | 학습자가 SID/DID/RID와 파라미터를 직접 이해하고 hex를 조립해 raw 필드에 입력하고 전송한다. 세션 제어, 보안 접근, 센서 읽기, 강제구동, DTC, 모션(웨이포인트와 자유모션 포함) 등 모든 진단 요청이 이 하나의 경로로 이루어진다 |
| CR3 | MQTT 발행/구독 | CR2에서 조립된 raw를 실제로 발행하고 응답을 구독(§3) |
| CR4 | 응답 디코딩/표시 | raw → 물리값/문자열 디코딩, 긍정/부정/에러 구분 표시(§4.2). 모션의 진행중(0x78)/완료/실패 상태도 동일하게 디코딩해 표시 |
| CR5 | 세션 유지 | TesterPresent(0x3E)는 학습자가 매번 수동 전송하지 않도록 백그라운드에서 2초 이내 주기로 자동 발행. 세션 유지는 실습 대상이 아니라 필요조건이므로 자동화. 사용자가 진단 화면을 벗어나거나 `10 01`로 기본세션 복귀를 요청하는 등 더 이상 세션 유지가 필요 없는 시점에는 백그라운드 발행을 중단한다 |
| CR6 | 상태/에러 처리 | RCI online/offline(LWT), robot connected/disconnected, 타임아웃("로봇 무응답") 표시 |
| CR7 | 로봇 상태 모니터 (자동 폴링) | 관절각, TCP 자세, robot_mode, safety_mode 등을 200~500ms 주기로 자동 폴링해 표시하는 상시 대시보드. CR2와 별개(상황 파악용, 프로토콜 조립 연습 대상 아님) |
| CR8 | 비상정지 버튼 (예외) | 언제든 즉시 호출 가능한 전용 버튼. `31 02 03 [rid]`(stopRoutine)을 직접 코딩 없이 즉시 발행 |

## 3. MQTT 인터페이스 계약

RCI 기능명세서 §4와 동일한 스키마를 사용해야 통신이 성립한다.

### 3.1 브로커

| 항목 | 값 |
|---|---|
| 위치 | 클라우드 호스팅 (클라우드 담당이 구축, 운영) |
| RCI 접속 | RCI가 이 브로커에 클라이언트로 접속. 접속 정보를 RCI 담당에게 전달 필요 |
| 포트 | 1883 (기본), TLS/인증 사용 시 해당 정보 공유 |
| 프로토콜 | MQTT 3.1.1 이상 |

학습용이라 보안(TLS/인증)은 기본 미사용이나, 클라우드 브로커가 요구하면 자격증명과 인증서를 RCI 담당에게 제공한다.

### 3.2 토픽

| 토픽 | 방향 | 발행자 | QoS | Retained |
|---|---|---|---|---|
| `minigit/req/urrobot` | 명령 | 웹앱 | 1 | N |
| `minigit/resp/urrobot` | 응답 | RCI | 1 | N |
| `minigit/error/urrobot` | 에러 | RCI | 1 | N |
| `minigit/status/rci-ur` | RCI 생존 | RCI | 1 | Y (+LWT) |

웹앱은 `minigit/req/urrobot`을 발행하고 `minigit/resp/urrobot`, `minigit/error/urrobot`, `minigit/status/rci-ur`를 구독한다.

### 3.3 페이로드 (JSON)

```jsonc
// 요청 (웹앱 발행)
{ "id": "u-0001", "raw": "22 01 01", "timeout_ms": 1000 }
//  id        : 요청-응답 상관용 고유 문자열 (웹앱 생성)
//  raw       : UDS 유효 페이로드 hex (필러 없음, 가변 길이)
//  timeout_ms: 선택(기본 1000). 전원 제어 등 장시간 작업은 상향

// 긍정 응답 (RCI 발행)
{ "id": "u-0001", "type": "positive", "raw": "62 01 01 FC 7C FC AB 03 F9 FB C6 FC 7E 00 03" }

// 부정 응답
{ "id": "u-0001", "type": "negative", "raw": "7F 22 31", "nrc": "31" }

// 진행중 통지 (전원 on, 브레이크 해제, 모션 등 장시간 작업 — RC카 세트와 다른 점, §1 참조)
{ "id": "u-0002", "type": "negative", "raw": "7F 2F 78", "nrc": "78" }

// 에러
{ "id": "u-0003", "type": "error", "reason": "robot_unreachable", "message": "로봇 무응답" }
//  reason ∈ { "robot_unreachable", "dashboard_error", "internal_error" }

// RCI 상태 (retained)
{ "state": "online", "robot": "connected" }   // LWT(RCI 비정상 종료 시): { "state": "offline" }
```

### 3.4 표기 및 처리 규칙

- hex 표기: 대문자, 바이트 공백 구분, `0x` 접두어 없음. 예 `"62 01 01 FC 7C"`, `nrc`="31"
- `id`: 웹앱이 생성, RCI가 그대로 에코. 동시에 하나의 요청만 진행(단일 세션) 권장
- `type` 판별: raw 첫 바이트가 `7F`면 부정, 아니면 긍정
- 프레임 크기: MQTT는 CAN과 달리 8바이트 제한이 없다. 학습자는 UDS 페이로드를 있는 그대로 raw로 조립해 보내면 되고, 별도의 분할 전송(ISO-TP 같은 것)을 신경 쓸 필요가 없다
- QoS1 사용으로 인한 중복 수신 가능성이 있으므로, 웹앱은 동일 `id`를 다시 받으면 이미 처리한 응답으로 보고 화면에 다시 반영하지 않아야 한다

## 4. 요청 조립 / 응답 디코딩 규칙

### 4.1 요청 조립 (학습자가 직접 수행)

- 요청 포맷: `[SID] [파라미터...]`
- 학습자는 §5의 서비스와 DID/RID 표를 보고 이 포맷에 맞춰 raw 문자열을 직접 작성한다
- 예 (센서 읽기): `[0x22] [DID_H] [DID_L]` → `"22 01 07"` (로봇 모드 읽기)
- 예 (모션, 웨이포인트): `[0x31] [0x01] [RID_H] [RID_L] [웨이포인트 인덱스]` → `"31 01 03 03 01"`
- 예 (모션, 자유 관절 이동): `[0x31] [0x01] [RID_H] [RID_L] [6축 목표각 12바이트] [속도 1바이트] [가속도 1바이트]` → `"31 01 03 01 00 00 FC 7C 00 00 FC 7C 00 00 00 00 1E 1E"`

### 4.2 응답 디코딩 (raw → 표시값)

- 긍정 응답: 첫 바이트 = 요청 SID + 0x40. 이후 데이터는 §5 인코딩표대로 해석한다
  - 예: `62 01 07 07` → DID 0x0107(로봇 모드), 값 7 = RUNNING
  - 예: `62 01 0A BB E4` → DID 0x010A(로봇 전압), 0xBBE4 = 48100mV = 48.1V
- 부정 응답: `7F [SID] [NRC]` → §5.8 NRC표로 이름과 메시지를 매핑한다
- 진행중 응답: `7F [SID] 78` (nrc="78")을 받으면 아직 작업이 끝나지 않았다는 뜻이다. 같은 `id`로 최종 응답이 다시 발행되므로, 화면에는 "진행중" 상태로 표시하고 최종 응답을 기다린다

## 5. UDS 프로토콜 사양 (클라우드가 구현할 대상)

값은 UR3 진단 통신 사양서 확정본과 동일하다. 아래는 웹앱 구현에 필요한 형태로 재정리한 것이다.

### 5.1 서비스(SID) 목록

| SID | 서비스 | 긍정 응답 SID | 용도 |
|---|---|---|---|
| 0x10 | DiagnosticSessionControl | 0x50 | 세션 시작/전환 |
| 0x11 | ECUReset | 0x51 | 가상 더미 ECU 리셋(하단 설명 참조) |
| 0x14 | ClearDiagnosticInformation | 0x54 | DTC 소거 |
| 0x19 | ReadDTCInformation | 0x59 | DTC 읽기 |
| 0x22 | ReadDataByIdentifier | 0x62 | 로봇 상태/사양 읽기 |
| 0x27 | SecurityAccess | 0x67 | 보안 접근 |
| 0x2E | WriteDataByIdentifier | 0x6E | 설정 데이터 쓰기 |
| 0x2F | InputOutputControlByIdentifier | 0x6F | 로봇 강제 구동(프로그램 재생, 속도, 전원, 안전 복구, 그리퍼) |
| 0x31 | RoutineControl | 0x71 | 모션 실행 |
| 0x3E | TesterPresent | 0x7E | 세션 유지 |

**0x11 ECUReset에 대한 설명**: UDS 표준상 이 서비스의 논리적 대상은 진단 대상 ECU, 즉 로봇 컨트롤러다. 하지만 실제 로봇 컨트롤러를 원격으로 리셋시키는 것은 지원하지 않는다(안전상 원격 전원 재기동을 이 경로로 수행하지 않는다). 그래서 이 요청에 대해서는 RCI가 실제 로봇에 아무 영향도 주지 않고 "리셋되었다"는 응답만 생성하는 가상의 더미 ECU 역할을 한다. 실질적으로 벌어지는 일은 RCI 자신의 세션/보안/제어권 상태 초기화뿐이다.

```
요청: 11 01     응답: 51 01
```

### 5.2 세션 제어 (0x10)

| SF | 세션 | 용도 |
|---|---|---|
| 0x01 | defaultSession | 기본 |
| 0x03 | extendedDiagnosticSession | 쓰기, 강제구동, 모션 실행 |

```
요청: 10 03      응답: 50 03 00 32 01 F4   (P2=50ms, P2*=5000ms)
```

확장 세션 유지: 학습자가 `3E 00`을 2초 이내 주기로 직접 코딩으로 보내야 한다(미발행 시 5초 후 RCI가 default 세션으로 되돌린다). 응답 `7E 00`.

### 5.3 로봇 상태 읽기 (0x22, DID 0x01xx)

| DID | 항목 | 응답 길이 | 타입 | 디코딩 |
|---|---|---|---|---|
| 0x0101 | 조인트 각도(6축) | 12B | 6×int16 | 0.1도 단위, 값/10 = 도 |
| 0x0102 | 조인트 속도(6축) | 12B | 6×int16 | 0.1도/초 단위, 값/10 = 도/초 |
| 0x0103 | 조인트 온도(6축) | 12B | 6×int16 | 0.1도(섭씨) 단위, 값/10 = 도 |
| 0x0104 | 조인트 전류(6축) | 12B | 6×int16 | mA 단위, 값/1000 = A |
| 0x0105 | TCP 위치(x, y, z) | 6B | 3×int16 | 0.1mm 단위, 값/10 = mm |
| 0x0106 | TCP 자세(rx, ry, rz) | 6B | 3×int16 | 0.001rad 단위, 값/1000 = rad |
| 0x0107 | 로봇 모드 | 1B | int8 | 값 자체가 의미(5.3.1 참조) |
| 0x0108 | 안전 모드 | 1B | uint8 | 값 자체가 의미(5.3.2 참조) |
| 0x0109 | 프로그램 실행 상태 | 1B | uint8 | 값 자체가 의미(5.3.3 참조) |
| 0x010A | 로봇 전압 | 2B | uint16 | mV 단위, 값/1000 = V |
| 0x010B | 로봇 전류 | 2B | uint16 | mA 단위, 값/1000 = A |
| 0x010C | 속도 스케일링 | 2B | uint16 | 0.1% 단위, 값/10 = % |
| 0x010D | 안전 상태 비트 | 2B | uint16 | 비트필드(5.3.4 참조). 가안, 실기에서 CB3 지원 여부 확인 필요 |
| 0x010E | 로드된 프로그램명 | 가변 | ASCII | 문자열 그대로 |
| 0x010F | 그리퍼 상태 | 1B | uint8 | 0~100(%), 0=완전히 열림, 100=완전히 닫힘. 별도 위치 감지 센서가 없다면 마지막 명령값을 그대로 반영(echo). 가안 |
| 0x0110 | 카메라 상태 | 1B | uint8 | 0=연결안됨, 1=연결됨 |

모든 다바이트 값은 빅엔디안이다. int16 음수는 2의 보수로 해석한다.

#### 5.3.1 로봇 모드 값 (0x0107)

| 값 | 의미 | 값 | 의미 |
|---|---|---|---|
| -1 | NO_CONTROLLER | 4 | POWER_ON |
| 0 | DISCONNECTED | 5 | IDLE |
| 1 | CONFIRM_SAFETY | 6 | BACKDRIVE |
| 2 | BOOTING | 7 | RUNNING |
| 3 | POWER_OFF | 8 | UPDATING_FIRMWARE |

#### 5.3.2 안전 모드 값 (0x0108)

| 값 | 의미 | 값 | 의미 |
|---|---|---|---|
| 1 | NORMAL | 6 | SYSTEM_EMERGENCY_STOP |
| 2 | REDUCED | 7 | ROBOT_EMERGENCY_STOP |
| 3 | PROTECTIVE_STOP | 8 | VIOLATION |
| 4 | RECOVERY | 9 | FAULT |
| 5 | SAFEGUARD_STOP | | |

#### 5.3.3 프로그램 실행 상태 값 (0x0109)

| 값 | 의미 | 값 | 의미 |
|---|---|---|---|
| 0 | STOPPING | 3 | PAUSING |
| 1 | STOPPED | 4 | PAUSED |
| 2 | PLAYING | 5 | RESUMING |

**PAUSED와 STOPPED의 차이**: PAUSED(일시정지)는 현재 실행 위치와 로봇 자세를 유지한 채로 실행만 멈춘 상태로, 이후 RESUMING을 거쳐 멈춘 지점부터 이어서 실행할 수 있다. STOPPED(정지)는 프로그램 실행을 완전히 종료한 상태로, 다시 실행하려면 PLAYING으로 처음부터 시작해야 한다.

#### 5.3.4 안전 상태 비트 (0x010D, 가안)

b0=normal, b1=reduced, b2=protective stopped, b3=recovery, b4=safeguard stopped, b5=system e-stop, b6=robot e-stop, b7=emergency stopped, b8=violation, b9=fault, b10=stopped due to safety

#### 예시 프레임

```
요청: 22 01 07     응답: 62 01 07 07              # 로봇 모드 RUNNING
요청: 22 01 0A     응답: 62 01 0A BB E4            # 48100mV = 48.1V
요청: 22 01 01     응답: 62 01 01 FC 7C FC AB 03 F9 FB C6 FC 7E 00 03
                                                    # [-90.0, -85.3, 101.7, -108.2, -89.8, 0.3]도
요청: 22 01 0F     응답: 62 01 0F 32               # 그리퍼 50% 닫힘
요청: 22 01 55     응답: 7F 22 31                  # 미정의 DID
```

### 5.4 사양/식별 정보 (0x22 읽기 / 0x2E 쓰기, DID 0xF1xx)

| DID | 항목 | 타입 | 디코딩 | 쓰기 가능 |
|---|---|---|---|---|
| 0xF199 | SW 업데이트 날짜 | 3B BCD | YYMMDD (26 07 27 → 2026-07-27) | 가능 |
| 0xF195 | SW 버전 (PolyScope) | 가변 ASCII | 문자열 그대로 (예 "3.15.8") | 불가 |
| 0xF18C | 시리얼 번호 | 가변 ASCII | 문자열 그대로. 가안, 실기에서 CB3가 시리얼 번호를 직접 제공하는지 확인 필요(현재는 RCI 설정 파일에 수기 입력한 값을 반환) | 가능 |
| 0xF1A0 | 로봇 IP 주소 | 4B uint8×4 | IPv4 옥텟 그대로 (예 C0 A8 01 65 → 192.168.1.101) | 가능 |

**0xF1A0 설명**: 이 값을 쓰면 실제 UR3 컨트롤박스의 네트워크 설정이 바뀌는 것이 아니라, RCI가 접속을 시도할 대상 IP 주소가 RCI 설정 파일에 저장된다. RCI는 기존 연결을 끊고 새 IP로 재접속을 시도한다. 값이 실제 로봇의 IP와 다르면 로봇의 IP가 바뀌는 것이 아니라 RCI가 접속에 실패한다. 실제 로봇의 IP를 변경하려면 UR 컨트롤박스의 PolyScope 화면에서 직접 설정해야 하며, 이 프로토콜로는 변경할 수 없다.

0x2E 쓰기 전제조건: 확장 세션 + 보안 접근 완료(미충족 시 `7F 2E 33` / `7F 2E 22`).

#### 예시 프레임

```
요청: 22 F1 99     응답: 62 F1 99 26 07 27          # 2026-07-27
요청: 22 F1 A0     응답: 62 F1 A0 C0 A8 01 65        # 192.168.1.101

요청: 2E F1 A0 C0 A8 01 66  응답: 6E F1 A0           # 확장세션+보안완료 후 IP 변경
요청: 2E F1 A0 C0 A8 01 66  응답: 7F 2E 33           # 보안 미완료 상태에서 쓰기 시도
요청: 2E F1 95 33 2E 31 35  응답: 7F 2E 31           # 쓰기 불가 항목
```

### 5.5 강제 구동 (0x2F, DID 0x02xx)

포맷: `2F [DID_H] [DID_L] [IOControlParameter] [제어데이터...]`
IOControlParameter: `0x03`=강제 조정(shortTermAdjustment), `0x00`=제어권 반환(returnControlToECU)

#### 5.5.1 프로그램 실행 제어 (0x0201)

이미 로드되어 있는 프로그램을 재생/정지/일시정지시키는 명령이다.

| 항목 | 내용 |
|---|---|
| 제어 데이터 | 1B: 0=정지, 1=재생, 2=일시정지 |
| 취득/제어 소스 | Dashboard `stop` / `play` / `pause` |
| 전제조건 | 확장 세션(보안 접근 불필요) |
| 왜 보안이 필요 없나 | 이미 로드된 프로그램을 재생/정지/일시정지하는 것은 일상적인 조작이고, 로봇의 안전 설정(속도 제한 등)은 그대로 유지된 채 동작하기 때문 |
| returnControlToECU(0x00) | 정지 상태로 복귀 |

```
요청: 2F 02 01 03 01     응답: 6F 02 01 03 01        # 프로그램 재생
요청: 2F 02 01 00        응답: 6F 02 01 00            # 정지(제어권 반환)
```

#### 5.5.2 속도 슬라이더 (0x0202)

UR 로봇은 PolyScope에 실제 실행 속도를 0~100%로 조절하는 슬라이더 기능이 있다. 이 값은 프로그램 재생이든 모션 명령(0x31)이든 관계없이 로봇이 실제로 움직이는 속도에 배율로 적용되는 안전장치다. 예를 들어 슬라이더가 50%면 요청한 속도의 절반으로만 움직인다.

| 항목 | 내용 |
|---|---|
| 제어 데이터 | 1B: 0~100(%) |
| 취득/제어 소스 | RTDE IO `speed_slider_fraction` |
| 전제조건 | 확장 세션(보안 접근 불필요) |
| returnControlToECU(0x00) | 100%로 복귀 |

```
요청: 2F 02 02 03 32     응답: 6F 02 02 03 32         # 속도 슬라이더 50%
```

#### 5.5.3 전원/브레이크 (0x0203)

UR 로봇은 전원이 꺼지면 각 관절 모터에 물리적 브레이크가 걸려 팔이 중력으로 떨어지지 않도록 고정된다. 전원을 켠 뒤에도 이 브레이크는 자동으로 풀리지 않고, "브레이크 해제" 명령을 별도로 내려야 팔이 움직일 수 있는 상태가 된다.

| 항목 | 내용 |
|---|---|
| 제어 데이터 | 1B: 0=전원 끄기, 1=전원 켜기, 2=브레이크 해제 |
| 취득/제어 소스 | Dashboard `power off` / `power on` / `brake release` |
| 전제조건 | 보안 접근 완료 필요(미충족 시 `7F 2F 33`) |
| 왜 보안이 필요한가 | 전원을 켜고 브레이크를 해제하는 것은 로봇을 실제로 움직일 수 있는 상태로 만드는 조작이라, 아무나 실행하면 위험할 수 있어 보안 접근을 요구한다 |
| 소요 시간 | 브레이크 해제는 수 초가 걸려 진행중 통지(`7F 2F 78`)가 먼저 오고 최종 응답이 이어진다 |
| returnControlToECU(0x00) | 개념 없음, `7F 2F 31` 반환 |

```
요청: 2F 02 03 03 02     중간: 7F 2F 78               # 브레이크 해제, 진행중 통지
          최종: 6F 02 03 03 02
요청: 2F 02 03 03 01     응답: 7F 2F 33               # 보안 미완료 상태에서 전원 제어
```

#### 5.5.4 안전 복구 (0x0204)

로봇이 안전 이벤트로 멈췄을 때 이를 정상 상태로 되돌리는 명령이다.

| 값 | 동작 | 설명 |
|---|---|---|
| 1 | 보호정지 해제 (unlock protective stop) | 충돌 등으로 감지되는 보호정지(비상정지보다는 약한 수준의 안전정지)를 풀어 다시 동작 가능하게 만든다. UR은 정지 발생 후 최소 5초가 지나야 해제를 허용한다 |
| 2 | 안전 팝업 닫기 (close safety popup) | 안전 이벤트 발생 시 티치펜던트 화면에 뜨는 확인 팝업을 원격으로 닫는다 |
| 3 | 안전 재시작 (restart safety) | 더 심각한 안전 결함이 발생했을 때 로봇의 안전 서브시스템 자체를 재시작한다 |

| 항목 | 내용 |
|---|---|
| 제어 데이터 | 1B: 1/2/3 (위 표) |
| 취득/제어 소스 | Dashboard `unlock protective stop` / `close safety popup` / `restart safety` |
| 전제조건 | 보안 접근 완료 필요(미충족 시 `7F 2F 33`) |
| 왜 보안이 필요한가 | 안전 정지 상태를 해제하는 것은 로봇이 멈춘 이유를 무시하고 다시 움직이게 만드는 조작이라 보안 접근을 요구한다 |
| returnControlToECU(0x00) | 개념 없음, `7F 2F 31` 반환 |

```
요청: 2F 02 04 03 01     응답: 7F 2F 37               # 보호정지 후 5초 미경과 unlock 거부
```

#### 5.5.5 그리퍼 제어 (0x0206)

| 항목 | 내용 |
|---|---|
| 제어 데이터 | 1B: 0~100 (%). 0=완전히 열림, 100=완전히 닫힘 |
| 취득/제어 소스 | UR 컨트롤박스 I/O를 통한 위치 조절. 정확한 신호 방식(아날로그 출력 전압 또는 디지털 신호 조합)은 가안, 실제 배선 확인 필요 |
| 전제조건 | 확장 세션(보안 접근 불필요, 0x0201/0x0202와 동일한 수준) |
| NRC 케이스 | 0x31(범위 밖, 101 이상), 0x13(길이) |
| returnControlToECU(0x00) | 개념 없음, `7F 2F 31` 반환 |

```
요청: 2F 02 06 03 32     응답: 6F 02 06 03 32         # 그리퍼 50%만 닫기
요청: 2F 02 06 03 65     응답: 7F 2F 31               # 101은 범위 밖
```

**0x0201과 모션 명령(0x31)의 관계**: UR 컨트롤러는 로봇에 새로운 동작(모션 명령이든 프로그램 재생이든)을 지시하는 순간, 이미 진행 중이던 다른 동작을 중단시킨다. 그래서 모션 명령이 실행 중일 때 0x0201로 프로그램을 재생하려 하면 `7F 2F 22`가, 반대로 프로그램 재생 중에 모션 명령을 시도하면 `7F 31 22`가 돌아온다(§5.6 참조).

### 5.6 보안 접근 (0x27) / 루틴 제어 (0x31)

#### 5.6.1 보안 접근 (0x27)

| 단계 | 요청 | 응답 |
|---|---|---|
| Seed 요청 | `27 01` | `67 01 11 22 33 44` (Seed = 0x11223344, 고정값) |
| Key 전송 | `27 02 55 66 77 88` | `67 02` (Key = 0x55667788, 고정값이 일치하면 성공) |

Key가 3회 연속 틀리면 10초간 잠금된다(`7F 27 36` 이후 잠금 기간 중 `7F 27 37`).

**보안 경고**: Seed/Key가 고정값이므로 이 절차는 재전송 공격을 막는 실제 보안 기능이 아니며, 세션/보안 절차의 흐름을 학습하기 위한 교육용 장치다. 한 번 캡처한 메시지를 그대로 재전송해도 인증이 통과된다.

```
요청: 27 02 00 00 00 00     응답: 7F 27 35            # 잘못된 키
```

#### 5.6.2 루틴 제어 — 모션 실행 (0x31, RID 0x03xx)

임의 관절/TCP 이동과 사전정의 웨이포인트 이동을 다룬다. RoutineControl은 시작(startRoutine), 중단(stopRoutine), 결과 조회(requestRoutineResults) 세 개의 서브펑션으로 이루어진다.

| RID | 이름 | 파라미터 | 필요 권한 |
|---|---|---|---|
| 0x0301 | MoveJoint | 6축 목표각(12B, 0.1도 단위) + 속도(1B, %) + 가속도(1B, %) | 확장 세션 + 보안 접근 완료 |
| 0x0302 | MoveLinear | TCP 위치(6B, 0.1mm) + TCP 자세(6B, 0.001rad) + 속도(1B, %) + 가속도(1B, %) | 확장 세션 + 보안 접근 완료 |
| 0x0303 | MoveToWaypoint | 웨이포인트 인덱스(1B) | 확장 세션 |
| 0x0305 | Wave (인사 동작 시연) | 속도(1B, %) + 가속도(1B, %) + 반복횟수(1B, 1~10) | 확장 세션 + 보안 접근 완료 |
| 0x0306 | TableTour (모서리 순회+그리퍼 시연) | 속도(1B, %) + 가속도(1B, %) + 그리퍼반복횟수(1B, 1~10) | 확장 세션 + 보안 접근 완료 |

자유 관절/TCP 이동(0x0301, 0x0302)은 사전정의 웨이포인트 이동(0x0303)보다 위험도가 높아 보안 접근을 추가로 요구한다(0x0203/0x0204와 같은 수준). Wave(0x0305)/TableTour(0x0306)도 큰 자유 동작이라 같은 수준의 권한을 요구한다. 둘 다 다른 RID와 달리 파라미터 길이가 3바이트로 고정 14바이트가 아니므로, raw hex 조립 UI에서 RID별 파라미터 길이를 안내할 때 주의가 필요하다.

**요청 흐름**

```
1. 시작:      31 01 [RID] [파라미터...]  ->  71 01 [RID] 00        # 즉시 접수(accepted)
2. 진행 확인: 31 03 [RID]                 ->  7F 31 78              # 아직 진행중
   (원하는 시점에 반복해서 보내 확인)
3. 완료 확인: 31 03 [RID]                 ->  71 03 [RID] 01 [결과 데이터] [실행시간]   # 성공
                                          또는 71 03 [RID] 02 [중단시점 데이터] [사유코드]  # 실패
4. 중단(언제든): 31 02 [RID]              ->  71 02 [RID] 00
```

**stopRoutine은 로봇 통신이 살아있는 한 항상 성공한다**: `31 02 [RID]`를 보내면 RCI는 요청에 적힌 RID와 무관하게 현재 실제로 실행 중인 모션을 멈춘다. 동시에 하나의 모션만 실행 가능하므로 어떤 RID를 실행 중인지 구분할 필요가 없다. 실행 중인 모션이 없어도 항상 `71 02 [RID] 00`을 반환하며 실패하지 않는다. 단, 로봇 통신이 두절된 상태에서는 정지 명령이 실제로 전달됐는지 확인할 수 없으므로 다른 서비스와 동일하게 `7F 31 22`를 반환한다.

#### 예시 프레임 (MoveJoint)

```
요청: 31 01 03 01 00 00 FC 7C 00 00 FC 7C 00 00 00 00 1E 1E
      (관절 목표각 [0.0, -90.0, 0.0, -90.0, 0.0, 0.0]도, 속도 30%, 가속도 30%)
응답: 71 01 03 01 00

요청: 31 03 03 01           응답: 7F 31 78              # 진행중
요청: 31 03 03 01           응답: 71 03 03 01 01 00 00 FC 7C 00 00 FC 7C 00 00 00 00 00 64
                                                          # 성공, 최종 관절각, 실행시간 10.0초

요청: 31 02 03 01           응답: 71 02 03 01 00         # 언제든 중단 가능
```

#### NRC 매핑

| 상황 | 응답 |
|---|---|
| default 세션에서 시도 | `7F 31 7F` |
| 자유 모션에서 보안 미완료 | `7F 31 33` |
| 목표값이 범위 밖 | `7F 31 31` |
| 미정의 RID | `7F 31 31` |
| 이미 실행 중인 모션에 새로 시작 시도 | `7F 31 21` |
| 시작한 적 없는 RID에 결과 조회 | `7F 31 24` |
| 로봇 통신 두절 중 시도 | `7F 31 22` |
| 프로그램 재생(0x0201) 중 모션 시도 | `7F 31 22` |

#### 5.6.3 루틴 제어 — 이미지 캡처 (0x31, RID 0x0304)

가안, 추후 논의 필요. 현재 방향은 startRoutine으로 촬영을 트리거하고, requestRoutineResults 응답에는 이미지 데이터 자체가 아니라 촬영 완료 여부와 이미지를 가져올 수 있는 참조값만 담는 것이다. 실제 이미지 파일 전달 방식(URL, 별도 토픽 등)은 확정되지 않았다.

### 5.7 DTC (0x19 / 0x14)

DTC는 3바이트 코드 + 1바이트 상태(0x08 = confirmed)로 구성된다. 감지되면 상태가 0x08로 설정되고, 원인이 해소되어도 상태는 그대로 유지된다(소거는 0x14로만 가능).

| DTC 코드 | 항목 | 발생 조건 |
|---|---|---|
| 0x900002 | 로봇 통신 두절 | RTDE 수신 두절 또는 Dashboard TCP 재접속 실패 |
| 0xB10001 | 비상정지 (E-Stop) | 안전 모드 = 6 또는 7 |
| 0xB10002 | 보호정지 (Protective Stop) | 안전 모드 = 3 |
| 0xB10003 | 세이프가드 정지 | 안전 모드 = 5 |
| 0xB10004 | 안전 위반/폴트 | 안전 모드 = 8 또는 9 |
| 0xC20101 | 조인트 과온 | 조인트 온도 6축 중 1축 이상이 60.0도 초과 |
| 0xC20201 | 로봇 저전압 | 로봇 전압이 44.0V 미만 |
| 0xC20301 | 카메라 연결 끊김 | 카메라 상태(DID 0x0110) 확인 실패 |

```
요청: 19 02 08     응답: 59 02 B1 00 02 08          # confirmed DTC 조회 (보호정지 발생 상태)
요청: 14 FF FF FF  응답: 54                          # 전체 소거
```

0x900002 설정 중에는 0x22, 0x2F, 0x31 요청에 `7F [SID] 22`가 반환된다.

### 5.8 NRC (부정 응답 코드)

`7F [SID] [NRC]` 형식. 이 문서에서 실제로 쓰이는 NRC만 정리한다.

| NRC | 이름 | 의미 |
|---|---|---|
| 0x10 | generalReject | 일반 거부 |
| 0x11 | serviceNotSupported | 미지원 서비스 |
| 0x12 | subFunctionNotSupported | 미지원 서브펑션 |
| 0x13 | incorrectMessageLengthOrInvalidFormat | 길이/포맷 오류 |
| 0x21 | busyRepeatRequest | 이미 실행 중인 작업이 있어 새 요청을 받을 수 없음 |
| 0x22 | conditionsNotCorrect | 조건 불충족 (로봇 통신 두절, 다른 동작과 충돌 등) |
| 0x24 | requestSequenceError | 요청 순서 오류(시작 안 한 루틴의 결과 조회 등) |
| 0x31 | requestOutOfRange | 요청 범위 밖(잘못된 DID/RID, 파라미터 범위 초과) |
| 0x33 | securityAccessDenied | 보안 접근 거부 |
| 0x35 | invalidKey | 잘못된 키 |
| 0x36 | exceededNumberOfAttempts | 키 시도 횟수 초과 |
| 0x37 | requiredTimeDelayNotExpired | 지연시간 미경과 |
| 0x78 | responsePending | 처리 중, 최종 응답이 뒤이어 온다 |
| 0x7F | serviceNotSupportedInActiveSession | 현재 세션에서 미지원 서비스 |

## 6. 시나리오 흐름

### 6.1 로봇 상태 읽기

```
[학습자] "로봇 모드가 궁금하다" → raw "22 01 07" 조립
 → publish req {"id":"u-0001","raw":"22 01 07"}
 ← resp {"id":"u-0001","type":"positive","raw":"62 01 07 07"}
[화면] 07 = RUNNING 으로 디코딩해 표시
```

### 6.2 보안 접근 후 쓰기

```
10 03  → 50 03 ...           확장 세션 진입
27 01  → 67 01 11 22 33 44   Seed = 0x11223344
27 02 55 66 77 78 → 67 02    Key 전송, 인증 성공
2E F1 A0 C0 A8 01 66 → 6E F1 A0    로봇 IP 쓰기
```

### 6.3 모션 실행

```
[학습자] 관절 이동 요청 조립 → raw "31 01 03 01 00 00 FC 7C 00 00 FC 7C 00 00 00 00 1E 1E"
 → publish req {"id":"u-0002","raw":"..."}
 ← resp {"id":"u-0002","type":"positive","raw":"71 01 03 01 00"}   # 접수됨

[학습자] 잠시 후 진행 상태 확인 → raw "31 03 03 01"
 ← resp {"id":"u-0003","type":"negative","raw":"7F 31 78","nrc":"78"}   # 아직 진행중

[학습자] 다시 확인 → raw "31 03 03 01"
 ← resp {"id":"u-0004","type":"positive","raw":"71 03 03 01 01 ...(최종 관절각)... 00 64"}   # 완료
```

### 6.4 보호정지 발생 → 조회 → 복구

```
[UR3]    보호정지 발생 (안전 모드 = 3)
[RCI]    DTC 0xB10002 상태 0x08 설정

[학습자] DTC 조회 → raw "19 02 08"
 ← resp raw "59 02 B1 00 02 08"

[학습자] (5초 경과 후) 보호정지 해제 시도 → raw "2F 02 04 03 01"
 ← resp raw "6F 02 04 03 01"   # 성공

[학습자] DTC 소거 → raw "14 FF FF FF"
 ← resp raw "54"
```

## 7. UI 기능 상세 요청

### 7.1 직접 코딩 인터페이스 (CR2)

- raw hex 문자열을 직접 입력하는 입력창과 전송 버튼을 제공한다
- `id`는 자동 생성한다(학습자가 신경 쓸 필요 없음), `timeout_ms`는 선택 입력(비우면 기본값 사용)
- 응답은 원문 raw와 함께, §5 규칙에 따라 해석한 값을 나란히 보여준다(긍정/부정/진행중/에러 구분)
- 이전에 보낸 요청과 응답을 이력으로 남겨 다시 참조할 수 있게 한다

### 7.2 로봇 상태 모니터 (CR7)

- 관절각(0x0101), TCP 자세(0x0105, 0x0106), 로봇 모드(0x0107), 안전 모드(0x0108), 로봇 전압(0x010A), 그리퍼 상태(0x010F), 카메라 상태(0x0110) 등을 200~500ms 주기로 자동 폴링해 표시한다
- 폴링 주기와 대상 DID는 웹앱 재량이나, 과도한 폴링은 지양한다(§8 참조)
- 안전 모드가 정상(NORMAL)이 아닐 때는 시각적으로 눈에 띄게 강조한다

### 7.3 비상정지 버튼 (CR8)

- 화면 어디서든 항상 접근 가능한 고정 위치에 노출한다(화면 전환이나 스크롤과 무관)
- 클릭 시 즉시 고정된 RID(예: `31 02 03 01`)로 stopRoutine을 발행한다. RCI는 요청에 적힌 RID와 무관하게 실제 실행 중인 모션을 멈추므로, 웹앱이 어떤 모션이 진행 중인지 따로 기억할 필요가 없다
- 다른 버튼과 명확히 구분되는 색상과 크기로 표시한다

## 8. 제약 및 참고

- 동시 1 사용자, 1 세션을 가정한다. 요청은 직렬 처리(응답 또는 타임아웃 후 다음 요청)를 권장하되, 정지/취소류 요청(`31 02 ...`)은 우선 처리된다(§5.6.2 참조).
- 이 프로토콜은 ISO 14229(UDS) 표준을 그대로 따르는 것이 아니라, UDS의 서비스와 세션 모델, SID, NRC 개념을 차용한 MQTT 기반 학습용 프로토콜이다. SecurityAccess의 고정 Seed/Key(§5.6.1)도 실제 보안 기능이 아닌 교육용 장치다.
- RC카 세트와 달리, 요청을 해석하고 로봇을 실제로 제어하며 응답을 생성하는 것은 RCI가 담당한다. 응답 raw 바이트를 사람이 읽을 수 있는 값으로 디코딩하고 NRC 이름을 매핑하는 것은 웹앱이 담당한다(§1 참조).
- 이미지 캡처(§5.6.3)는 가안이며 추후 논의 대상이다.
- QoS1 사용으로 인한 중복 수신 가능성이 있으므로, 웹앱은 동일 `id`를 다시 받으면 이미 처리한 응답으로 보고 화면에 다시 반영하지 않아야 한다(§3.4 참조).
- 프로토콜 값의 단일 출처(SSOT, Single Source of Truth — 여러 문서 중 최종 기준으로 삼는 단일 출처)는 UR3 진단 통신 사양서다. 이 문서와 충돌하는 내용이 있으면 사양서를 우선한다.
