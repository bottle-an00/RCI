## 1. [RCI(HW)] 하드웨어 셋업

### 왜 필요한가

RCI가 동작할 물리 토대다. 이 항목이 끝나지 않으면 나머지 9개 중 어느 것도 착수할 수 없다. 세 가지가 각각 다른 이유로 필요하다.

**이중 네트워크**가 필요한 이유는 RCI가 로봇과 클라우드에 동시에 붙기 때문이다. 로봇은 유선 이더넷으로 같은 서브넷에서, 브로커는 Wi-Fi로 인터넷을 거쳐 접속한다. 인터페이스 두 개를 동시에 쓰는 구성이라 라우팅을 잘못 잡으면 한쪽이 조용히 끊긴다.

**ur_rtde를 먼저 설치해보는 것**도 목적이다. 내부가 C++이라 아키텍처에 맞는 wheel이 없으면 Boost 컴파일까지 포함한 소스 빌드로 넘어간다. 이 사실을 개발 후반에 발견하면 일정 전체가 밀린다.

**그리퍼와 카메라**는 신호 방식과 연결 판정 기준이 정해지지 않으면 DID 0x0206, 0x010F, 0x0110과 DTC 0xC20301을 구현할 수 없다. 특히 그리퍼는 위치 감지 센서가 없어서, 0x010F가 실측값이 아니라 RCI가 마지막으로 보낸 명령값을 되돌려주는 방식이 될 수밖에 없다. 이 제약을 여기서 확정해야 5번 항목의 설계가 정해진다.

### 어떻게 구현하는가

**1. RSP4에 OS / Python3 / ur_rtde 설치**

Raspberry Pi OS는 64비트를 권장한다. 64비트 쪽이 `ur_rtde` wheel이 존재할 가능성이 높아 소스 빌드를 피할 수 있다. `pip3 install -r requirements.txt`로 설치하고, wheel이 없어 소스 빌드로 넘어가면 Boost와 CMake를 먼저 설치한다. 설치 절차와 소요 시간을 기록해 재설치나 다른 보드 셋업에 재사용한다.

**2. 이더넷↔컨트롤박스 / Wi-Fi↔클라우드 이중 네트워크 구성**

- `eth0`: 컨트롤박스와 같은 서브넷의 고정 IP
- `wlan0`: 클라우드 브로커 경로
- 기본 게이트웨이는 `wlan0`에만 둔다. 로봇 대역 트래픽이 인터넷으로 나가지 않게 하기 위함이다
- 로봇 IP는 PolyScope > Settings > System > Network에서 확인해 [config.py](../config.py)에 반영한다
- [read_state.py](../scripts/read_state.py)와 [dashboard_test.py](../scripts/dashboard_test.py)로 양쪽 통신을 확인한다

**3. 그리퍼 신호 방식 확인 및 0~100% 매핑 캘리브레이션**

그리퍼 데이터시트로 요구 신호 방식(디지털 출력 조합 또는 아날로그 출력)을 확인하고, 컨트롤박스 I/O 채널을 정해 배선한다. `RTDEIOInterface`로 해당 채널에 값을 직접 써보며 개폐를 확인하고, 0%(완전 열림)에서 100%(완전 닫힘)까지의 신호 매핑표를 만든다. 응답이 선형이 아니면 보정값을 함께 기록한다. 위치 감지 센서 부재를 실물로 확인하고 DID 0x010F를 마지막 명령값 반환 방식으로 확정한다.

**4. 카메라 연결 테스트 및 camera_link 모듈 구현**

먼저 연결 판정 기준을 정한다. 디바이스 노드 존재 확인은 가볍지만 드라이버가 먹통인 상태를 정상으로 오판한다. 프레임 1장 획득은 확실하지만 500ms 주기 감시에 쓰기에는 비용이 크다. 둘 사이에서 선택하고 근거를 남긴다. `camera_link` 모듈에 판정 함수와 결과 캐시를 두고, 8번 항목의 `dtc_monitor`가 호출할 인터페이스를 정리한다. 연속 몇 회 실패해야 DTC 0xC20301로 볼지도 함께 정의한다. 순간 실패 한 번에 고장 코드를 세우면 오경보가 잦아진다.

### 완료 기준

- [ ] `read_state.py`와 `dashboard_test.py`가 정상 출력한다
- [ ] 로봇 통신과 브로커 경로가 동시에 유지된다
- [ ] 그리퍼가 0%, 50%, 100% 명령에 각각 다르게 반응하고 신호 매핑표가 확정된다
- [ ] 카메라 연결과 분리에 따라 판정이 1과 0으로 전환된다
- [ ] `ur_rtde` 설치 절차가 재현 가능한 형태로 문서화된다

### 근거

RCI 기능명세서 §2, §3.2 / 로봇 기능명세서 §2.1, §2.3, §3.3.5, §5.1, §7 A3

## 2. [RCI(기반)] robot_interface - 로봇 통신 계층

### 왜 필요한가

로봇과 통신하는 세 개의 채널을 한 계층으로 묶는다. 위쪽의 모든 서비스가 이 계층을 통해서만 로봇에 접근하므로, 여기서 인터페이스를 정리해두지 않으면 서비스마다 로봇 접속 코드가 중복된다.

**RTDE 수신 스레드**가 필요한 이유는 응답 속도다. ReadDataByIdentifier 요청이 올 때마다 로봇에 물어보면 느리고 로봇 부하도 커진다. 초당 125회 들어오는 상태 데이터를 백그라운드 스레드가 받아 캐시에 덮어써두고, 요청이 오면 즉시 꺼내 응답한다.

**Dashboard 클라이언트**는 프로그램 재생, 전원, 브레이크, 안전 복구 같은 조작에 쓴다. RTDE로는 할 수 없는 일이다. 프로토콜은 텍스트 한 줄을 주고받는 단순한 형태지만, 성공과 실패를 응답 문자열로 판정해야 한다. 명령마다 어떤 문자열이 성공인지 실기에서 확인해 표로 만들어두지 않으면 6번 항목의 모든 핸들러가 판정을 제각각 하게 된다.

**RTDEControl 연결관리**가 별도로 필요한 이유는 이 인터페이스의 특성 때문이다. 연결되는 순간 로봇 안에 제어 스크립트를 올려두고 연결이 유지되는 동안 상주시킨다. RCI가 비정상 종료되면 스크립트가 남아 다음 실행 때 충돌한다. 또 프로그램 재생과 경쟁하므로 재생 전에 명시적으로 끊어야 한다.

**safety_status_bits 확인을 이 항목에 넣는 이유**는 순서 때문이다. RTDE는 컨트롤박스가 지원하지 않는 필드가 출력 레시피에 하나라도 있으면 연결 자체를 거부한다. CB3 미지원으로 판명되면 DID 0x010D를 사양에서 빼고 안전 모드(0x0108)로 대체해야 하는데, 이 판단이 늦을수록 되돌릴 작업이 늘어난다.

### 어떻게 구현하는가

**1. RTDE 수신 스레드 (출력 레시피 12종, 125Hz, 캐시 TTL 1s, 5s 재접속)**

`RTDEReceiveInterface`에 출력 레시피 12종을 등록한다.

```
actual_q, actual_qd, actual_current, joint_temperatures, actual_TCP_pose,
robot_mode, safety_mode, safety_status_bits, runtime_state, speed_scaling,
actual_robot_voltage, actual_robot_current
```

수신 전용 스레드가 루프를 돌며 값을 캐시에 갱신하고 **갱신 시각도 함께 기록**한다. 마지막 갱신 후 1초가 지나면 캐시를 무효로 간주하는데, 이 판정이 5번 항목에서 `7F 22 22`(conditionsNotCorrect)를 반환할 근거가 된다. 두절을 감지하면 상태 플래그를 전환하고 5초 간격으로 재접속을 시도한다. 메인 스레드와 동시에 접근하므로 락 또는 딕셔너리 원자적 교체로 보호한다.

**2. Dashboard TCP 클라이언트**

29999 포트 TCP 클라이언트를 만들고 소켓 타임아웃을 5초로 둔다. 명령 끝에는 개행 문자를 붙여야 컨트롤박스가 명령의 끝으로 인식한다. 사용할 명령 12종을 함수로 래핑한다.

```
play, stop, pause, get loaded program, power on, power off, brake release,
unlock protective stop, close safety popup, restart safety, PolyscopeVersion, safetymode
```

각 명령의 성공과 실패 판정 문자열을 실기 응답 그대로 표로 작성한다. 재접속은 **소켓 close 완료를 확인한 뒤** 최대 1회 재시도한다. close 확인을 건너뛰고 재연결하면 거부되거나 응답이 멎는 사례가 보고되어 있다.

**3. RTDEControl 연결관리 (기동 시 좀비 스크립트 정리, 명시적 disconnect, RTDE IO 초기화)**

`RTDEControlInterface` 연결과 해제를 한 곳에서 관리한다. RCI 기동 시 `isProgramRunning()`으로 상주 스크립트를 확인하고, 남아 있으면 `reuploadScript()`로 정리한 뒤 재연결한다. 6번 항목의 0x0201 재생 직전에 호출할 명시적 `disconnect` 함수를 제공한다. `RTDEIOInterface`도 여기서 초기화한다. 6번의 0x0202 속도 슬라이더와 0x0206 그리퍼가 이 채널을 쓴다.

**4. safety_status_bits CB3 지원 여부 확인**

`safety_status_bits`를 출력 레시피에 넣은 상태로 **가장 먼저** 연결을 시도한다. 연결이 거부되면 이 필드를 레시피에서 빼고, DID 0x010D를 안전 모드(0x0108)로 대체하는 방향으로 사양 변경을 문서에 반영한 뒤 클라우드 담당에게 공유한다(요청서 §9 액션 5).

### 완료 기준

- [ ] 캐시에서 12개 항목이 모두 최신값으로 읽힌다
- [ ] 랜선을 뽑으면 1초 내 캐시가 무효로 판정되고, 다시 꽂으면 자동 재접속된다
- [ ] `safety_status_bits` CB3 지원 여부가 확정되고 문서에 반영된다
- [ ] Dashboard 12개 명령이 전부 실기에서 응답을 받고 판정 문자열 표가 완성된다
- [ ] 프로세스를 강제 종료한 뒤 재기동해도 정상 연결된다
- [ ] `disconnect` 후 Dashboard `play`가 정상 동작하고 이후 재연결도 정상이다

## 3. [RCI(기반)] UDS 처리 구현

### 왜 필요한가

RCI를 UDS 서버로 만드는 뼈대다. 로봇과 무관해서 1번과 병행 착수가 가능하다.

**mqtt_client**는 웹앱과의 유일한 통로다. 특히 LWT를 반드시 걸어야 한다. RCI가 전원이 뽑히는 식으로 죽으면 스스로 종료를 알릴 수 없고, 웹앱은 그 상황과 "살아 있는데 응답만 없는 상태"를 구분할 수 없다. 접속할 때 브로커에 유언을 맡겨두면 연결이 끊기는 순간 브로커가 대신 알려준다.

**요청 큐**가 필요한 이유는 로봇 상태의 예측 가능성이다. 요청을 받는 즉시 처리하면 여러 건이 몰릴 때 로봇을 동시에 건드려 결과를 알 수 없게 된다. 그래서 한 번에 하나씩 처리한다. 예외가 하나 있는데 정지 요청(`31 02`)이다. 로봇이 움직이는 중에 정지 명령이 큐 뒤에 줄 서 있으면 위험하므로 대기 중인 다른 요청을 제친다. 이 우선순위 규칙이 사실상 소프트웨어 안전장치다.

**디스패처**는 모든 서비스의 공통 왕복 경로다. 웹앱이 보내는 것은 `"22 01 01"` 같은 문자열 하나뿐이므로, 바이트로 바꾸고 SID를 보고 담당 핸들러에게 넘기고 결과를 다시 UDS 응답 형식으로 조립해야 한다. 공통 검사(길이와 포맷, 미지원 서비스)도 여기서 하면 서비스마다 검사 누락이 제각각 생기는 것을 막을 수 있다.

**상태 저장소**가 필요한 이유는 초기화 누락을 막기 위해서다. RCI는 세션, 보안, 제어권, robot_busy_owner 네 개의 상태를 굴리는데, 이것들이 코드 여기저기 흩어지면 S3 타임아웃 같은 이벤트에서 일부만 초기화되는 버그가 생긴다. 명세는 네 가지를 모두 초기화하라고 요구하므로, 한 곳에 모으고 일괄 초기화 함수를 둔다.

**설정 JSON 스키마**에는 재시작 후에도 남아야 하는 값이 들어간다. 이 중 **웨이포인트 목록은 명세 어디에도 정의되어 있지 않아 여기서 처음 만들어야 한다.** RID 0x0303이 인덱스 1바이트를 받는데 그 인덱스가 가리키는 좌표가 문서에 없는 상태다.

### 어떻게 구현하는가

**1. mqtt_client**

`paho-mqtt`로 브로커에 접속한다. 호스트와 포트는 설정으로 외부화한다.

| 토픽 | 방향 | QoS | Retained |
|---|---|---|---|
| `minigit/req/urrobot` | 구독 | 1 | N |
| `minigit/resp/urrobot` | 발행 | 1 | N |
| `minigit/error/urrobot` | 발행 | 1 | N |
| `minigit/status/rci-ur` | 발행 | 1 | Y (+LWT) |

상태 토픽은 Retained로 `{"state":"online","robot":"connected"}`를 발행하고, LWT로 `{"state":"offline"}`을 등록한다. 수신 콜백에서 JSON을 파싱해(`id`, `raw`, `timeout_ms`) 요청 큐로 넘기고, 파싱 실패는 error 토픽으로 발행한다. 브로커 재접속 시 구독을 복원한다.

**2. 요청 큐 / 우선순위 스케줄러 / uds_server 디스패처 / 상태 저장소**

*요청 큐와 스케줄러*: 우선순위 2단계(기본, 최우선)로 충분하다. raw 첫 두 바이트가 `31 02`(stopRoutine)이면 최우선으로 분류하되, 향후 다른 정지 요청이 추가될 수 있으므로 분류를 별도 함수로 분리한다. 워커 스레드 하나가 큐에서 꺼내 순차 처리하고, P2(50ms)와 P2*(5000ms) 타이밍을 관리하며 9번 항목의 responsePending 처리기로 넘길 훅을 마련한다.

*디스패처*: raw hex 문자열을 바이트열로 파싱한다(대문자, 바이트 공백 구분, `0x` 접두어 없음). SID를 추출해 핸들러 테이블에서 조회하고, 미등록 SID는 `7F [SID] 11`(serviceNotSupported), 길이와 포맷 위반은 `7F [SID] 13`(incorrectMessageLengthOrInvalidFormat)으로 반환한다. 핸들러 호출 규약은 입력이 바이트열과 상태 컨텍스트, 출력이 응답 바이트열 또는 NRC다. 응답은 긍정이면 SID+0x40, 부정이면 `7F [SID] [NRC]`로 조립하고 hex 문자열로 재직렬화한다. JSON을 구성할 때 `id`를 에코하고, 첫 바이트가 0x7F면 `type`을 negative로 하고 `nrc` 필드를 추가한다. 핸들러 내부 예외를 잡아 error 토픽의 `internal_error`로 흘리는 안전망을 둔다. 핸들러 하나의 버그로 RCI 전체가 죽으면 안 된다.

*상태 저장소*: 아래를 인메모리로 관리하고 **일괄 초기화 함수**를 제공한다.

| 상태 | 값 |
|---|---|
| 세션 | defaultSession, extendedDiagnosticSession |
| 보안 | locked, seedIssued, unlocked, delayLock |
| 제어권 | 강제 구동 중인 DID 집합 |
| robot_busy_owner | NONE, URP_PROGRAM, MOTION_ROUTINE |
| 부가 | 그리퍼 마지막 명령값, 보호정지 발생 시각 |

**3. 설정 JSON 스키마**

| 키 | 내용 |
|---|---|
| `settings` | 0xF199(SW 업데이트 날짜), 0xF18C(시리얼 번호), 0xF1A0(로봇 IP) |
| `dtc` | 코드(3B)에서 상태(1B)로의 맵 |
| `waypoints` | 인덱스에서 6축 관절각으로의 목록. **신규 정의 항목** |

임시 파일에 쓰고 이름을 바꿔치기하는 방식으로 원자적 쓰기를 구현한다. 기동 시 로드하고, 파일이 없거나 깨졌으면 기본값으로 폴백한다. 여러 스레드가 접근하므로 락을 설계한다. 웨이포인트는 개수와 각 좌표를 정하고 모두 로봇 세이프티 존 안에 있는지 검토한다.

### 완료 기준

- [ ] 테스트 클라이언트에서 발행한 요청이 RCI에 도달한다
- [ ] RCI를 강제 종료하면 브로커가 `{"state":"offline"}`을 발행한다
- [ ] 나중에 접속한 구독자가 Retained 상태 메시지를 즉시 받는다
- [ ] 요청 여러 건을 연속 발행해도 순서대로 1건씩 처리되고, 대기 요청이 쌓인 상태에서 `31 02`가 먼저 실행된다
- [ ] 미등록 SID에 `7F [SID] 11`, 길이 오류에 `7F [SID] 13`을 반환한다
- [ ] 핸들러가 예외를 던져도 프로세스가 유지되고 error가 발행된다
- [ ] 일괄 초기화 호출 시 네 상태가 모두 기본값으로 돌아간다
- [ ] 재시작 후 DTC, 설정값, 웨이포인트가 복원되고 저장 중 강제 종료해도 파일이 깨지지 않는다

## 4. [RCI(서비스)] 세션 / 보안 / 리셋(0x10/0x3E/0x27/0x11) 구현

### 왜 필요한가

진단 장비의 두 겹 관문을 만든다. 나머지 모든 서비스가 이 두 상태를 전제조건으로 검사하므로 서비스 계층에서 가장 먼저 구현한다.

**첫 번째 관문은 세션**이다. defaultSession에서는 읽기만 되고, extendedDiagnosticSession에 들어가야 쓰기와 강제 구동, 루틴 실행이 열린다. 그런데 확장 세션을 열어놓고 자리를 뜨면 로봇이 언제든 움직일 수 있는 상태로 방치된다. 그래서 UDS는 진단 장비가 붙어 있음을 주기적으로 알리지 않으면 자동으로 되돌리는 장치를 둔다. 그 신호가 TesterPresent이고 제한 시간이 S3 타이머다. **타임아웃 시 초기화 대상에 실행 중인 모션이 포함된다.** 세션이 풀리는 순간 움직이던 로봇을 그대로 두면 위험하므로 정지시킨 뒤 되돌린다.

**두 번째 관문은 SecurityAccess**다. 전원 켜기, 브레이크 해제, 안전 정지 해제, 자유 모션은 확장 세션만으로 부족하다. 다만 본 프로젝트는 Seed와 Key가 고정값이라 실제 보안 기능이 아니다. 캡처한 메시지를 그대로 재전송해도 통과한다. 이것은 의도된 설계로, 세션에서 보안을 거쳐 조작에 이르는 UDS 절차 흐름을 익히게 하려는 교육용 장치다.

**ECUReset을 여기 묶는 이유**는 동일한 일괄 초기화 경로를 쓰기 때문이다. UDS 표준에서 이 서비스의 대상은 진단 대상 ECU지만, 안전상 로봇을 원격으로 재기동시키지 않기로 했다. 그래서 RCI가 가상의 더미 ECU 역할을 해 로봇에는 아무 영향 없이 자기 상태만 초기화한다. 실습 중 상태가 꼬였을 때의 탈출구가 된다.

### 어떻게 구현하는가

**1. default↔extended 전환, P2/P2* 응답, S3 5s 타이머 및 만료 시 모션 정지 후 일괄 초기화**

0x10 핸들러에서 서브펑션 0x01(defaultSession)과 0x03(extendedDiagnosticSession)을 처리하고 `50 [SF] 00 32 01 F4`로 응답한다. `0x0032`가 P2(50ms), `0x01F4`가 P2*(500, 즉 5000ms)다. 미지원 서브펑션은 `7F 10 12`(subFunctionNotSupported)다.

S3 타이머 스레드가 5초 만료를 감시하고, 만료 시 아래 순서를 지킨다.

1. `robot_busy_owner`가 MOTION_ROUTINE이면 `stopJ()` 또는 `stopL()`을 **먼저** 호출한다
2. 세션을 defaultSession으로 되돌린다
3. 3번 항목의 일괄 초기화 함수를 호출해 보안을 locked로, 제어권을 전체 반환으로, `robot_busy_owner`를 NONE으로 되돌린다

`10 01` 요청도 같은 경로를 타게 한다.

**2. TesterPresent 처리**

`3E 00` 수신 시 S3 타이머를 리셋하고 `7E 00`으로 응답한다.

**3. 고정 Seed/Key 인증과 3회 실패 시 10초 잠금 (7F 27 36 → 37)**

| 요청 | 응답 | 상태 전이 |
|---|---|---|
| `27 01` (requestSeed) | `67 01 11 22 33 44` | locked → seedIssued |
| `27 02 55 66 77 88` (sendKey, 일치) | `67 02` | seedIssued → unlocked |
| `27 02 ...` (불일치) | `7F 27 35` (invalidKey) | 실패 카운터 증가 |
| 3회 연속 불일치 | `7F 27 36` (exceededNumberOfAttempts) | delayLock 진입, 10초 |
| 잠금 기간 중 요청 | `7F 27 37` (requiredTimeDelayNotExpired) | 유지 |
| 지연 경과 | | delayLock → locked, 카운터 초기화 |

requestSeed 없이 sendKey를 보내면 `7F 27 24`(requestSequenceError)를 반환한다.

**4. 0x11 소프트 리셋 (로봇 본체 무영향, 가상 더미 ECU). 0x11 지원 서브펑션 목록 확정 포함**

명세에는 `11 01` → `51 01` 예시만 있고 서브펑션 정의표가 없다. **지원 목록을 확정한다.** 기본안은 0x01만 지원하고 나머지는 `7F 11 12`로 반환하는 것이며, 결정 내용을 사양서에 반영한다.

리셋 처리는 세션 만료와 같다. `robot_busy_owner`가 MOTION_ROUTINE이면 정지를 선행하고 일괄 초기화 함수를 호출한다. 제어권 반환은 6번 항목의 DID별 반환 동작을 그대로 수행한다. 집합만 비우면 로봇은 강제 구동 상태로 남는다. 응답은 `51 [SF]`다.

**로봇 본체에 영향을 주지 않음을 확인한다.** Dashboard 명령을 보내지 않고 RTDE 연결도 유지한다.

### 완료 기준

- [ ] `10 03` → `50 03 00 32 01 F4`, `3E 00` → `7E 00`이고 타이머가 리셋된다
- [ ] extendedDiagnosticSession에서 5초간 TesterPresent를 끊으면 defaultSession으로 돌아가고 네 상태가 모두 초기화된다
- [ ] 모션 실행 중 세션이 만료되면 로봇이 정지한 뒤 상태가 초기화된다
- [ ] 틀린 Key 3회에 `7F 27 36`, 이후 10초간 `7F 27 37`, 경과 후 정상 시도가 가능하다
- [ ] `11 01` → `51 01`이고, 속도 슬라이더 50% 상태에서 리셋하면 100%로 복귀한다
- [ ] 리셋 후에도 RTDE 캐시가 계속 갱신된다

## 5. [RCI(서비스)] 데이터 읽기 / 쓰기(0x22/0x2E) 구현

### 왜 필요한가

진단의 핵심 기능이다. 조인트 각도, 온도, 안전 모드 같은 질문에 답하고, 웹앱의 상태 모니터도 이 서비스를 200~500ms마다 반복 호출해 화면을 갱신한다.

**작업의 실질은 단위 변환이다.** RTDE는 라디안, 섭씨, 암페어, 미터 같은 물리 단위의 실수로 값을 주는데 UDS 응답은 정해진 바이트 수의 정수여야 한다. 조인트 각도라면 라디안을 도로 바꾸고 10을 곱해 int16 2바이트에 담는다. 이 규칙을 정확히 지키지 않으면 웹앱이 디코딩한 값이 실제와 달라져도 알아차리기 어렵다. 로봇은 멀쩡히 동작하고 화면의 숫자만 틀리기 때문이다.

**DID의 출처가 셋이라 경로를 나눠야 한다.** 0x0101에서 0x010D까지는 RTDE 캐시에서 꺼내지만, 0x010E는 Dashboard에 물어봐야 해서 TCP 왕복이 필요하고, 0x010F는 위치 감지 센서가 없어 로봇에 물어볼 수 없으며, 0x0110은 로봇과 아예 무관한 카메라 확인이다.

**WriteDataByIdentifier에서는 0xF1A0의 의미를 정확히 구현하는 것이 핵심이다.** 이 값을 써도 UR3 컨트롤박스의 네트워크 설정은 바뀌지 않는다. 바뀌는 것은 RCI가 접속을 시도할 대상 IP뿐이라, 실제 로봇 IP와 다른 값을 쓰면 로봇 IP가 바뀌는 것이 아니라 RCI가 접속에 실패한다. 이 차이를 모르고 구현하면 IP를 바꿨는데 로봇이 안 붙는다는 혼란이 생긴다.

### 어떻게 구현하는가

**1. 0x01xx 상태 DID 16종 인코딩**

DID에서 RTDE 캐시 키로 가는 매핑 테이블을 만들고 인코딩한다. 모든 다바이트 값은 **빅엔디안**, int16 음수는 **2의 보수**다.

| DID | 원시 값 | 변환 | 길이 |
|---|---|---|---|
| 0x0101 조인트 각도 | `actual_q` (rad) | rad→deg, ×10 | 12B, 6×int16 |
| 0x0102 조인트 속도 | `actual_qd` (rad/s) | rad/s→deg/s, ×10 | 12B, 6×int16 |
| 0x0103 조인트 온도 | `joint_temperatures` (℃) | ×10 | 12B, 6×int16 |
| 0x0104 조인트 전류 | `actual_current` (A) | ×1000 (mA) | 12B, 6×int16 |
| 0x0105 TCP 위치 | `actual_TCP_pose[0..2]` (m) | m→0.1mm | 6B, 3×int16 |
| 0x0106 TCP 자세 | `actual_TCP_pose[3..5]` (rad) | ×1000 | 6B, 3×int16 |
| 0x0107 로봇 모드 | `robot_mode` | 그대로 | 1B int8 |
| 0x0108 안전 모드 | `safety_mode` | 그대로 | 1B uint8 |
| 0x0109 실행 상태 | `runtime_state` | 그대로 | 1B uint8 |
| 0x010A 로봇 전압 | `actual_robot_voltage` (V) | ×1000 (mV) | 2B uint16 |
| 0x010B 로봇 전류 | `actual_robot_current` (A) | ×1000 (mA) | 2B uint16 |
| 0x010C 속도 스케일링 | `speed_scaling` (0~1) | ×1000 | 2B uint16 |
| 0x010D 안전 상태 비트 | `safety_status_bits` | 비트필드 그대로 | 2B uint16 |

응답은 `62 [DID_H] [DID_L] [데이터]`로 조립한다. 캐시 TTL 1초를 넘겼거나 RTDE 미접속이면 `7F 22 22`(conditionsNotCorrect)를 반환하고 DTC 0x900002를 설정한다. 미정의 DID는 `7F 22 31`(requestOutOfRange)이다. **읽기는 세션과 무관하게 허용한다.** 2번 항목에서 0x010D가 CB3 미지원으로 판명되었다면 해당 DID를 제거하고 `7F 22 31`로 처리한다.

**2. Dashboard 계열 TTL 5s 캐시, 그리퍼 마지막 명령값 echo**

| DID | 구현 |
|---|---|
| 0x010E 로드된 프로그램명 | Dashboard `get loaded program` 호출 후 프로그램명만 추출. **TTL 5초 캐시**를 적용해 폴링이 잦아도 로봇에는 5초에 한 번만 요청한다. ASCII 가변 길이 |
| 0x010F 그리퍼 상태 | 3번 항목 상태 저장소의 그리퍼 마지막 명령값을 1바이트로 반환. 한 번도 명령하지 않았을 때의 초기값을 정의한다 |
| 0x0110 카메라 상태 | 1번 항목 `camera_link`의 판정 결과를 0 또는 1로 반환 |

사양 대역 0xF1xx도 같은 핸들러에서 처리한다. 0xF199는 3바이트 BCD(YYMMDD), 0xF195는 Dashboard `PolyscopeVersion` 결과에 TTL 5초 캐시, 0xF18C는 실기에서 `get serial number` 지원 여부를 확인해 지원하면 그 값을 미지원이면 설정 파일 수기값으로 폴백(로봇 기능명세서 A4), 0xF1A0은 4바이트 IPv4 옥텟이다.

**로봇 두절 시 응답 정책을 확정한다.** 명세는 두절 중 0x22 요청에 `7F 22 22`를 반환하라고 일괄 규정하지만, 0x010F와 0x0110, 그리고 0xF1xx 상당수는 로봇과 무관하게 답할 수 있다. 출처별로 나누는 것을 기본안으로 검토하고 결정을 사양서에 반영한다.

**3. 0x2E 쓰기 (확장세션+보안, 0xF195 거부, 0xF1A0 쓰기 시 새 IP 재접속)**

전제조건을 먼저 검사한다. extendedDiagnosticSession이 아니면 `7F 2E 22`(conditionsNotCorrect), SecurityAccess 미완료면 `7F 2E 33`(securityAccessDenied)이다.

쓰기 가능 항목은 0xF199(3바이트 BCD 검증), 0xF18C(ASCII 문자열), 0xF1A0(4바이트 옥텟 검증)이다. 0xF195는 읽기 전용이므로 `7F 2E 31`(requestOutOfRange), 길이 불일치는 `7F 2E 13`을 반환한다. 긍정 응답은 `6E [DID_H] [DID_L]`이다.

0xF1A0 쓰기 후 재접속 절차는 다음과 같다. 새 IP를 원자적으로 저장하고, 기존 RTDE와 Dashboard 연결을 모두 종료한 뒤, 새 IP로 재접속을 시도한다. 재접속이 실패해도 응답 자체는 `6E F1 A0`으로 정상 반환하되 두절 상태가 되므로 8번 항목의 `dtc_monitor`가 DTC 0x900002를 세우고 9번 항목이 status 토픽에 `robot:"disconnected"`를 발행하게 된다.

### 완료 기준

- [ ] 0x01xx 16종과 0xF1xx 4종 DID가 전부 정상 응답한다
- [ ] 음수 각도가 2의 보수로 정확히 인코딩된다 (-90.0도 → `FC 7C`)
- [ ] 명세 부록의 예시 프레임과 바이트 단위로 일치한다
- [ ] 0x010E를 5초 안에 반복 호출해도 Dashboard TCP 요청은 1회만 발생한다
- [ ] 그리퍼 명령 후 `22 01 0F`가 그 값을 반환하고, 카메라를 분리하면 `22 01 10`이 `00`을 반환한다
- [ ] 랜선 분리 시 확정한 정책대로 응답한다
- [ ] `2E F1 A0 C0 A8 01 66` → `6E F1 A0`, 보안 미완료 시 `7F 2E 33`, 0xF195 쓰기 시 `7F 2E 31`
- [ ] IP 변경 후 새 IP로 재접속을 시도하고, 재시작해도 값이 유지된다

## 6. [RCI(서비스)] 강제 구동(0x2F) 구현

### 왜 필요한가

InputOutputControlByIdentifier는 진단 장비가 정상 제어를 가로채 액추에이터를 직접 조작하는 서비스다. 실제 정비에서 부품이 살아 있는지 확인하는 표준 절차이며, 여기서는 프로그램 실행 제어, 속도 슬라이더, 전원과 브레이크, 안전 복구, 그리퍼 다섯 항목이 대상이다.

**권한이 두 등급으로 나뉘는 이유**를 알고 구현해야 한다. 0x0201, 0x0202, 0x0206은 extendedDiagnosticSession만 요구한다. 이미 로드된 프로그램을 돌리거나 속도를 줄이는 것은 일상적 조작이고 로봇의 안전 설정이 그대로 유지되기 때문이다. 반면 0x0203은 로봇을 움직일 수 있는 상태로 만드는 조작이고 0x0204는 멈춘 이유를 무시하고 다시 움직이게 하는 조작이라, SecurityAccess까지 요구한다.

**가장 까다로운 부분은 0x0201과 RoutineControl의 충돌 처리다.** UR 컨트롤러는 새 동작을 지시받는 순간 진행 중이던 동작을 중단시킨다. 그런데 `RTDEControlInterface`는 연결 중 로봇에 제어 스크립트를 상주시키므로, 이 상태로 프로그램을 재생하면 서로 간섭한다. 재생 전에 제어 연결을 명시적으로 끊고 재생이 끝나면 다시 붙이는 절차가 필요하다.

**returnControlToECU가 필요한 이유**는 진단이 끝났을 때 로봇을 원래 상태로 되돌리기 위해서다. 속도 슬라이더가 20%로 잠긴 채 남아 있으면 안 된다. 그런데 사용자가 반환을 깜빡하거나 웹앱이 갑자기 닫히는 경우가 있으므로, 세션이 끝나거나 타임아웃되면 전부 자동 반환해야 한다. 이것을 각 핸들러에 흩어놓으면 반드시 빠뜨리는 항목이 생기므로 집합으로 한 곳에서 관리한다.

### 어떻게 구현하는가

요청 포맷은 `2F [DID_H] [DID_L] [IOControlParameter] [제어데이터]`다. IOControlParameter는 0x03이 shortTermAdjustment, 0x00이 returnControlToECU다. 공통으로 세션 검사, 길이 검사(`7F 2F 13`), 범위 검사(`7F 2F 31`)를 수행한다.

**1. 0x0201 프로그램 실행 제어 (RTDEControl 선disconnect → play → 재생 종료 폴링 감지 후 reuploadScript 재연결)**

extendedDiagnosticSession을 검사한다. `robot_busy_owner`가 MOTION_ROUTINE이면 재생 요청에 `7F 2F 22`(conditionsNotCorrect)를 반환한다. 재생 허용 시 순서는 다음과 같다.

1. `RTDEControlInterface`를 명시적으로 disconnect한다
2. Dashboard `play`를 실행한다
3. `robot_busy_owner`를 URP_PROGRAM으로 전이한다

제어데이터 0은 `stop`, 2는 `pause`다. **재생 종료는 `runtime_state`를 폴링해 감지한다.** STOPPED 또는 PAUSED로 바뀌면 `reuploadScript()`로 `RTDEControlInterface`를 재연결하고 `robot_busy_owner`를 NONE으로 되돌린다. 프로그램이 스스로 끝나는 경우가 있으므로 요청 기반이 아니라 상태 폴링으로 감지해야 한다. 프로그램이 로드되지 않은 상태에서 재생을 시도하면 `7F 2F 22`다. returnControlToECU는 정지 상태로 복귀시키고 `6F 02 01 00`을 반환한다.

**2. 0x0202 속도 슬라이더**

extendedDiagnosticSession을 검사한다. `RTDEIOInterface`로 `speed_slider_mask`를 1로 설정한 뒤 `speed_slider_fraction`에 값을 100으로 나눈 실수를 넣는다. returnControlToECU는 100%로 복귀시킨다.

**3. 0x0203 전원 / 브레이크**

SecurityAccess 완료를 검사한다. 미충족이면 `7F 2F 33`(securityAccessDenied)이다. 제어데이터 0은 Dashboard `power off`, 1은 `power on`, 2는 `brake release`다. `power on`과 `brake release`는 2초 이상 걸리므로 9번 항목의 responsePending 처리기를 통해 `7F 2F 78`을 먼저 발행하고 완료 시 같은 `id`로 최종 응답을 재발행한다. returnControlToECU는 개념이 없으므로 `7F 2F 31`이다.

**4. 0x0204 안전 복구 (보호정지 후 5s 제약)**

SecurityAccess 완료를 검사한다. 제어데이터 1은 Dashboard `unlock protective stop`, 2는 `close safety popup`, 3은 `restart safety`다.

**5초 제약**은 8번 항목의 `dtc_monitor`가 `safety_mode`가 3으로 전이할 때 상태 저장소에 기록한 발생 시각을 참조한다. 5초가 지나지 않았으면 `7F 2F 37`(requiredTimeDelayNotExpired)을 반환한다. 로봇이 거부하기 전에 RCI가 먼저 판단하는 구조다. `restart safety`도 시간이 걸리므로 responsePending 처리 대상이다. returnControlToECU는 `7F 2F 31`이다.

**5. 0x0206 그리퍼, returnControl DID별 반환 동작 및 세션 종료 / 타임아웃 / 리셋 시 전체 자동 반환**

*그리퍼*: extendedDiagnosticSession을 검사한다. 1번 항목의 매핑표대로 I/O에 출력하고, 성공 시 상태 저장소의 그리퍼 마지막 명령값을 갱신한다(0x010F 읽기에 반영). 101 이상은 `7F 2F 31`이다.

*returnControlToECU DID별 반환 동작*:

| DID | 반환 동작 |
|---|---|
| 0x0201 프로그램 실행 제어 | 정지 상태로 복귀, `6F 02 01 00` |
| 0x0202 속도 슬라이더 | 100%로 복귀, `6F 02 02 00` |
| 0x0203 전원 / 브레이크 | 개념 없음, `7F 2F 31` |
| 0x0204 안전 복구 | 개념 없음, `7F 2F 31` |
| 0x0206 그리퍼 | 개념 없음, `7F 2F 31` |

*전체 자동 반환*: 강제 구동에 성공한 DID를 집합에 추가하고, 세션 종료와 S3 타임아웃, ECUReset 시 4번 항목의 일괄 초기화에서 호출한다. 집합만 비우지 말고 위 표의 반환 동작을 실제로 수행해야 한다.

DID 0x0205는 사양에 정의되어 있지 않다. 의도적 결번인지 정의 누락인지 확정해 사양서에 명시하고, 미정의 DID는 `7F 2F 31`로 처리한다. Dashboard 명령의 성공과 실패는 2번 항목의 판정표로 판단하고, 실패 시 error 토픽에 `dashboard_error`를 발행한다.

### 완료 기준

- [ ] `2F 02 01 03 01` → `6F 02 01 03 01`이고 프로그램이 실제로 재생되며 `robot_busy_owner`가 URP_PROGRAM이 된다
- [ ] 프로그램이 스스로 종료된 뒤 `RTDEControlInterface`가 자동 재연결되어 루틴 실행이 다시 가능하다
- [ ] `2F 02 02 03 32` → PolyScope 슬라이더가 50%로 이동하고, `2F 02 02 00` → 100%로 복귀한다
- [ ] `2F 02 06 03 32` → 그리퍼가 절반 닫히고 `22 01 0F`가 그 값을 반환한다. `03 65`(101)는 `7F 2F 31`이다
- [ ] 보안 미완료 시 `2F 02 03 03 01` → `7F 2F 33`, 완료 후 브레이크 해제가 `7F 2F 78`을 거쳐 `6F 02 03 03 02`로 끝난다
- [ ] 보호정지 직후 `2F 02 04 03 01` → `7F 2F 37`, 5초 후 성공한다
- [ ] 속도 슬라이더 50% 상태에서 S3 타임아웃 시 자동으로 100%로 복귀한다
- [ ] `2F 02 05 ...` → `7F 2F 31`이고 결번 여부가 사양서에 명시된다

## 7. [RCI(서비스)] 루틴 실행(0x31) 구현

### 왜 필요한가

RoutineControl은 로봇을 실제로 움직이는, 이 프로젝트에서 가장 위험한 서비스다. 설계상 중요한 점이 셋 있다.

**비동기 처리가 필요한 이유**는 정지 명령을 받기 위해서다. 모션은 수 초가 걸리는데 그동안 응답을 붙들고 있으면 그 사이 stopRoutine도 처리할 수 없다. 그래서 startRoutine은 접수만 하고 즉시 `71 01 [RID] 00`을 반환하며, 진행 상황은 웹앱이 requestRoutineResults로 따로 물어본다. 이 구조 덕분에 정지 요청이 언제든 끼어들 수 있다.

**다층 안전장치가 필요한 이유**는 로봇 쪽 방어선만으로 부족하기 때문이다. 1차 방어선은 로봇 자체의 세이프티 존(PolyScope Installation 설정)이고 UDS로 바꿀 수 없다. 그 위에 소프트웨어로 목표값 화이트리스트 검증, 속도와 가속도 상한 제한, 동시 1개만 허용, 런어웨이 방지 타임아웃을 얹는다. 세이프티 존 안이라도 예상 밖 경로로 움직일 수 있으므로 소프트웨어 검증을 생략하면 안 된다.

**stopRoutine이 비상정지 경로**라는 점이 세 번째다. 웹앱의 비상정지 버튼이 그대로 이 요청을 발행한다. 그래서 RID와 무관하게 동작하고(동시에 하나만 실행되므로 구분할 필요가 없고 웹앱이 상태를 기억할 필요도 없다), 항상 성공하며(비상정지가 실패를 반환하면 안 된다), 큐 최우선으로 처리된다.

명세 공백 셋이 이 항목에서 확정된다. 웨이포인트 테이블(0x0303이 인덱스만 받고 좌표가 없다), 실행시간 필드 사양, 실패 사유코드 체계다.

### 어떻게 구현하는가

**1. startRoutine**

전제조건을 아래 순서로 검사한다.

| 순서 | 조건 | 응답 |
|---|---|---|
| 1 | `robot_busy_owner`가 URP_PROGRAM | `7F 31 22` conditionsNotCorrect |
| 2 | `robot_busy_owner`가 MOTION_ROUTINE | `7F 31 21` busyRepeatRequest |
| 3 | 로봇 통신 두절 | `7F 31 22` conditionsNotCorrect |
| 4 | defaultSession | `7F 31 7F` serviceNotSupportedInActiveSession |
| 5 | 0x0301, 0x0302에서 SecurityAccess 미완료 | `7F 31 33` securityAccessDenied |
| 6 | 미정의 RID | `7F 31 31` requestOutOfRange |

0x0303은 extendedDiagnosticSession만 요구한다. 자유 관절과 TCP 이동이 사전정의 웨이포인트 이동보다 위험도가 높기 때문이다.

파라미터를 디코딩한다.

| RID | 파라미터 |
|---|---|
| 0x0301 MoveJoint | 6축 목표각(12B, 0.1도) + 속도(1B, %) + 가속도(1B, %) |
| 0x0302 MoveLinear | TCP 위치(6B, 0.1mm) + TCP 자세(6B, 0.001rad) + 속도(1B) + 가속도(1B) |
| 0x0303 MoveToWaypoint | 웨이포인트 인덱스(1B) |

**웨이포인트 테이블을 정의한다.** 개수와 각 인덱스의 6축 관절각을 정하고 3번 항목의 설정 JSON에 등록한다. 모든 좌표가 세이프티 존 안에 있는지 실기로 확인하고, 존재하지 않는 인덱스는 `7F 31 31`로 반환한다.

**목표값 화이트리스트를 검증한다.** 각 축의 허용 각도 범위와 TCP 허용 작업 영역을 정의하고, 벗어나면 `7F 31 31`을 반환한다. 속도와 가속도는 서버측 상한으로 제한해 웹앱이 100%를 보내도 상한을 넘지 않게 한다.

통과하면 `moveJ()` 또는 `moveL()`을 `async=True`로 호출하고 `robot_busy_owner`를 MOTION_ROUTINE으로 전이한 뒤 런어웨이 방지 타이머를 시작한다(30~60초 가정, 로봇 기능명세서 A6). 즉시 `71 01 [RID_H] [RID_L] 00`을 반환한다.

**2. requestRoutineResults 폴링 (7F 31 78 → 결과 조립)**

시작한 적 없는 RID를 조회하면 `7F 31 24`(requestSequenceError)다. `getAsyncOperationProgress()`를 폴링해 진행 중이면 `7F 31 78`(responsePending)을 반환하고, 완료되면 결과를 조립한 뒤 `robot_busy_owner`를 NONE으로 되돌린다.

*성공 응답 사양 확정*: `71 03 [RID_H] [RID_L] 01 [결과 데이터] [실행시간]`. 결과 데이터는 최종 관절각 또는 최종 TCP다. **실행시간은 2바이트 uint16, 0.1초 단위로 확정한다.** 명세 예시의 `00 64`가 10.0초와 일치한다. 확정 내용을 사양서에 명시한다.

*실패 사유코드 체계 정의*: `71 03 [RID_H] [RID_L] 02 [중단시점] [사유코드]`. 사유코드 값 목록이 정의되어 있지 않으므로 새로 만든다. 최소한 아래를 구분해야 한다.

- 사용자 정지 요청(stopRoutine)
- 런어웨이 타임아웃 초과
- 안전 정지 발생(보호정지, 비상정지)
- 로봇 통신 두절
- `RTDEControlInterface` 호출 실패

웹앱이 이 코드를 이름으로 매핑하므로 확정 목록을 사양서와 클라우드 요청서에 반영하고 클라우드 담당에게 공유한다.

*런어웨이 타임아웃 처리*: 타이머가 만료됐는데 여전히 진행 중이면 RCI가 자체적으로 `stopJ()` 또는 `stopL()`을 호출하고 사유코드를 타임아웃으로 해서 실패 결과로 조립한다.

**3. stopRoutine (큐 최우선 / RID 무관 / 항상 성공)**

RID와 무관하게 `stopJ()` 또는 `stopL()`을 호출하고, `robot_busy_owner`를 NONE으로, 런어웨이 타이머를 해제한다. **실행 중인 모션이 없어도 항상** `71 02 [RID_H] [RID_L] 00`을 반환한다. 3번 항목의 우선순위 큐에서 최우선으로 처리되는지 확인한다.

### 완료 기준

- [ ] `31 01 03 01 ...` → `71 01 03 01 00`이 1초 이내에 반환되고 로봇이 목표 자세로 이동한다
- [ ] 이동 중 재전송하면 `7F 31 21`, defaultSession에서는 `7F 31 7F`, 보안 미완료 0x0301은 `7F 31 33`이고 0x0303은 통과한다
- [ ] 범위 밖 목표각에 `7F 31 31`을 반환하고 로봇이 움직이지 않는다
- [ ] 웨이포인트 테이블이 확정되고 전 인덱스가 세이프티 존 안에서 정상 도달한다
- [ ] 진행 중 `31 03 03 01` → `7F 31 78`, 완료 시 결과가 반환되고 실행시간이 실제 소요와 일치한다
- [ ] 시작한 적 없는 RID 조회에 `7F 31 24`를 반환한다
- [ ] 모션 중 `31 02 03 01` → 즉시 `71 02 03 01 00`이고 로봇이 실제로 정지한다. 모션이 없을 때도 같은 응답이다
- [ ] 런어웨이 타임아웃 초과 시 RCI가 스스로 정지시키고 실패 결과를 반환한다
- [ ] 실패 사유코드 목록이 사양서와 클라우드 요청서에 반영된다

### 근거

## 8. [RCI(서비스)] DTC 읽기/쓰기(0x19/0x14) 구현

### 왜 필요한가

DTC는 진단의 핵심 산출물이다. **지금 이상이 있다가 아니라 언젠가 이상이 있었다를 기록**하는 것이 요점이다. 실제 차량에서 간헐적 증상만으로 원인을 찾기 어려울 때 ECU에 남은 DTC가 결정적 단서가 된다. 그래서 본 프로젝트도 원인이 해소돼도 상태를 유지하고, 소거는 ClearDiagnosticInformation으로만 가능하게 한다. 정비사가 확인하고 조치했다고 명시적으로 선언해야 지워지는 구조다.

**dtc_monitor가 저장소와 짝을 이루는 이유**는 역할이 다르기 때문이다. 저장소가 기록하는 곳이라면 monitor는 무엇을 기록할지 판단하는 곳이다. 웹앱이 묻지 않아도 RCI가 스스로 500ms마다 상태를 살펴 이상을 감지한다. 진단 장비가 수동적 조회 도구가 아니라 능동적 감시자가 되는 지점이다.

**보호정지 발생 시각 기록이 여기 들어가는 이유**는 6번 항목 때문이다. 0x0204의 5초 제약을 판정하려면 보호정지가 언제 발생했는지 알아야 하는데, 그 시점을 아는 것은 `safety_mode` 전이를 감시하는 `dtc_monitor`뿐이다.

이 항목에서 정리할 것이 셋 있다. ReadDTCInformation의 응답 포맷(지원 서브펑션도 응답 구조도 미정이고, 특히 UDS 표준의 statusAvailabilityMask 바이트가 명세 예시에는 없다), 과온 임계값 문서 충돌(사양서와 로봇 기능명세서는 50.0℃, 클라우드 요청서는 60.0℃이고 SSOT는 사양서다), 정상 복귀 시 DTC 처리 정책(RCI 기능명세서 A1)이다.

### 어떻게 구현하는가

**1. DTC 저장 JSON**

`{코드(3B) → 상태(1B)}` 맵을 3번 항목의 JSON 영속 계층에 저장한다. 본 프로젝트는 상태 바이트로 0x08(confirmedDTC)만 사용한다. 설정과 소거 이력은 10번 항목의 로그에 남긴다.

**2. statusMask 조회 및 전체 소거**

*지원 서브펑션 확정*: 기본안은 0x02(reportDTCByStatusMask)만 지원하고 나머지는 `7F 19 12`(subFunctionNotSupported)로 반환하는 것이다. 웹앱이 개수만 먼저 알고 싶을 수 있으므로 0x01(reportNumberOfDTCByStatusMask) 추가 여부를 검토한다.

*응답 포맷 확정*: statusAvailabilityMask 바이트를 넣을지 결정한다. 넣으면 `59 02 [availabilityMask] [DTC 3B][status 1B] ...`로 UDS 표준에 부합하고, 빼면 `59 02 [DTC 3B][status 1B] ...`로 명세 예시에 부합한다. **웹앱 디코딩이 이 결정에 직접 걸려 있으므로 클라우드 담당과 반드시 공유한다.**

*조회와 소거*: statusMask로 필터링해 해당하는 DTC만 응답에 담고, 해당 없으면 목록이 빈 응답을 보낸다. 소거는 `14 FF FF FF`에 `54`로 응답한다. 특정 그룹 소거 지원 여부를 결정하고 미지원이면 `7F 14 31`이다. 조회와 소거 모두 세션과 무관하게 허용한다.

**3. dtc_monitor 500ms 주기 감시로 8종 발생 조건 판정**

2번 항목의 RTDE 캐시와 1번 항목의 `camera_link`를 읽어 판정한다.

| DTC | 발생 조건 |
|---|---|
| 0x900002 로봇 통신 두절 | RTDE 수신 두절 또는 Dashboard TCP 재접속 실패 |
| 0xB10001 비상정지 | `safety_mode`가 6 또는 7 |
| 0xB10002 보호정지 | `safety_mode`가 3 |
| 0xB10003 세이프가드 정지 | `safety_mode`가 5 |
| 0xB10004 안전 위반 / 폴트 | `safety_mode`가 8 또는 9 |
| 0xC20101 조인트 과온 | 6축 중 1축 이상이 **50.0℃ 초과** |
| 0xC20201 로봇 저전압 | 로봇 전압 **44.0V 미만** |
| 0xC20301 카메라 연결 끊김 | 카메라 상태 확인 실패(연속 실패 기준은 1번 항목에서 정의) |

감지하면 상태를 0x08로 설정하고 저장소에 기록한다.

**과온 임계값 문서 충돌을 정정한다.** 클라우드 요청서 §5.7의 60.0℃를 50.0℃로 수정하고 근거를 함께 기록한다. UR 안전 프로세서가 이 온도부터 경고 로그를 남기며, 실제 안전정지가 걸리는 약 85℃보다 미리 경보하려는 의도다.

**정상 복귀 시 DTC 처리 정책(A1)을 확정한다.** 유지할지 자동 소거할지 결정하고, 유지로 확정하면 RC카 세트와 동일 정책임을 명시한다.

임계값 근처에서 판정이 계속 뒤집히지 않도록 히스테리시스 또는 연속 N회 조건을 검토한다.

**4. 보호정지 발생 시각 기록**

`safety_mode`가 3으로 **전이하는 순간**의 시각을 3번 항목의 상태 저장소에 기록한다. 값이 3인 동안 매 주기 갱신하면 안 된다. 6번 항목의 0x0204가 이 값으로 5초 경과 여부를 판정한다.

### 완료 기준

- [ ] 랜선을 분리하면 0x900002가 설정되고, 재연결해도 DTC가 유지된다
- [ ] 티치펜던트 비상정지에 0xB10001, 보호정지에 0xB10002가 설정되고 발생 시각이 기록된다
- [ ] 카메라를 분리하면 0xC20301이 설정된다
- [ ] `19 02 08`로 설정된 DTC가 조회되고, `14 FF FF FF` → `54` 후 목록이 빈다
- [ ] 프로세스를 재시작해도 DTC가 유지된다
- [ ] 500ms 주기가 실제로 지켜지고 다른 요청 처리를 지연시키지 않는다
- [ ] ReadDTCInformation 지원 서브펑션과 응답 포맷이 확정되어 클라우드에 공유된다
- [ ] 과온 임계값이 50.0℃로 문서 간에 통일되고 A1 정책이 확정된다

## 9. [RCI(운영)] 응답 지연, 에러/상태 발행, 재접속 처리 구현

### 왜 필요한가

개별 서비스에 속하지 않고 시스템 전체에 걸치는 세 가지를 묶는다.

**responsePending이 필요한 이유**는 처리 시간이 긴 작업 때문이다. 대부분의 요청은 밀리초 단위로 끝나지만 전원 켜기, 브레이크 해제, 안전 재시작은 로봇이 물리적으로 동작해야 해서 수 초가 걸린다. 그냥 기다리게 하면 웹앱은 요청이 실패한 것인지 처리 중인 것인지 알 수 없다. UDS는 이 상황을 위해 요청은 정상 수신했고 처리 중이라는 중간 통지를 정의해뒀다. 형식상 부정 응답이지만 의미는 진행 중이며, 나중에 같은 `id`로 최종 응답이 온다. 각 핸들러가 알아서 구현하면 재발행 횟수 제한 같은 규칙이 제각각이 되므로 공통 장치로 만든다.

**error 토픽이 별도로 필요한 이유**는 UDS 프레임 자체를 만들 수 없는 상황이 있기 때문이다. 로봇 무응답, Dashboard 소켓 사망, RCI 내부 예외가 그렇다. 이런 것을 `7F [SID] [NRC]`로 표현하는 것은 부적절하다.

**status 토픽은 성격이 또 다르다.** 요청에 대한 답이 아니라 RCI가 스스로 알리는 상태 방송이다. 웹앱은 이것을 보고 요청을 보내보기 전에 RCI는 살아 있는데 로봇이 끊겼다는 상황을 알 수 있다.

**재접속 정책을 여기 묶는 이유**는 재접속의 성공과 실패가 곧 상태 전이이고 그때마다 발행해야 하기 때문이다. 명세는 상황별로 다른 방식을 요구하므로 규칙들이 흩어지지 않게 한곳에 모은다.

### 어떻게 구현하는가

**1. responsePending(0x78) 공통 처리기 구현**

핸들러가 이 작업은 오래 걸린다고 등록하면 나머지를 처리기가 맡는 구조로 만든다.

1. 등록 즉시 `7F [SID] 78`을 발행한다. 요청의 `id`를 그대로 쓴다
2. 백그라운드에서 실제 작업을 수행한다
3. 완료되면 **같은 `id`로 최종 응답을 재발행**한다
4. 5초를 넘기면 `7F [SID] 78`을 다시 발행한다. **최대 6회, 총 30초**까지다
5. 30초를 초과하면 발행을 멈추고 error 토픽에 `dashboard_error`를 발행해 종결한다

**0x78 대기 중에도 요청 큐가 막히지 않게 한다.** 이 작업이 진행되는 동안에도 stopRoutine 같은 최우선 요청은 처리되어야 한다.

적용 대상은 6번 항목의 0x0203 전원 켜기와 브레이크 해제, 0x0204 안전 재시작이다. 7번 항목 requestRoutineResults의 `7F 31 78`은 웹앱이 직접 폴링하는 구조라 재발행 없이 매 요청마다 돌려주면 된다.

**2. error 토픽 3종 publish**

| reason | 발행 시점 |
|---|---|
| `robot_unreachable` | 로봇 무응답 |
| `dashboard_error` | Dashboard 명령 실패, responsePending 30초 초과 |
| `internal_error` | RCI 내부 예외. 3번 항목 디스패처의 안전망에서 호출 |

페이로드는 `{"id": ..., "type": "error", "reason": ..., "message": ...}` 형식이다.

**3. status 토픽 상태 전이 시에만 publish**

`{"state":"online","robot":"connected"}` 또는 `"disconnected"`를 Retained로 발행한다. **값이 바뀌는 순간에만 발행한다.** 매 주기 발행하면 트래픽 낭비다.

**4. 상황별 재접속 정책**

| 상황 | 동작 |
|---|---|
| RTDE 수신 두절 | DTC 0x900002 설정, `robot:"disconnected"` 발행, 5초 간격 재접속 시도 |
| Dashboard 소켓 끊김 | **소켓 close 완료를 확인한 뒤** 재접속, 최대 1회 재시도 |
| RCI 기동 시 | `isProgramRunning()` 확인 후 `reuploadScript()`로 좀비 스크립트 정리하고 재연결(2번 항목) |
| 재접속 성공 | `robot:"connected"` 발행. **DTC는 유지한다.** 소거는 0x14로만 |
| 0xF1A0 쓰기 | 기존 연결을 즉시 종료하고 새 IP로 재접속(5번 항목) |

재접속에 성공해도 DTC를 지우지 않는 이유를 코드 주석에 남긴다. 일시적 두절이 있었다는 기록 자체가 진단 정보이기 때문이다.

LWT와의 일관성도 맞춘다. 정상 종료 시에는 `{"state":"offline"}`을 직접 발행하고 접속을 끊어 브로커가 LWT를 발행하지 않게 한다.

### 완료 기준

- [ ] 브레이크 해제 요청에 즉시 `7F 2F 78`을 반환하고, 완료 후 같은 `id`로 `6F 02 03 03 02`를 발행한다
- [ ] 오래 걸리는 상황에서 0x78이 5초 간격으로 재발행되고, 30초를 초과하면 `dashboard_error`로 종결한다
- [ ] 0x78 대기 중에도 `31 02`가 즉시 처리된다
- [ ] 랜선을 분리하면 `robot:"disconnected"`가 1회만 발행되고, 재연결하면 `connected`가 발행되되 DTC는 유지된다
- [ ] Dashboard 명령 실패에 `dashboard_error`, 핸들러 예외에 `internal_error`를 발행하고 프로세스는 유지된다
- [ ] RTDE 재접속이 5초 간격으로 반복되고 복구 시 자동으로 정상화된다

## 10. [RCI(운영)] 로깅 및 서비스 운영 구성

### 왜 필요한가

**로그 없이는 디버깅이 사실상 불가능하다.** 이유가 겹친다. 요청과 응답이 hex 바이트열이라 눈으로 이해하기 어렵고, 로봇 동작이 비동기라 문제 발생 시점과 증상이 나타나는 시점이 다르고, 상태 기계가 네 개 돌아가서 왜 `7F 31 22`가 나왔는지는 그 순간의 상태를 봐야 알 수 있고, 실기 테스트는 로봇이 물리적으로 움직이는 일이라 같은 상황을 반복 재현하기 번거롭다. 특히 `robot_busy_owner` 전이 로그가 중요하다. 0x0201과 RoutineControl의 상호배제가 가장 얽혀 있는 로직이라, 전이 이력이 없으면 거부 사유를 추적할 방법이 없다.

**운영 구성은 성격이 다르다.** 지금까지 만든 것은 터미널에서 실행하는 스크립트지만, RCI는 전원이 들어오면 알아서 떠 있어야 하는 장비다. 실습할 때마다 SSH로 붙어 켜야 한다면 진단 장비라고 할 수 없다. `systemd`로 등록하면 부팅 자동 시작과 비정상 종료 시 자동 재시작이 해결된다. 후자가 특히 중요하다. RCI가 죽으면 LWT로 offline이 발행되고 웹앱은 아무것도 할 수 없게 되는데, 자동 재시작이 걸려 있으면 몇 초 만에 복구되고 재기동 시 좀비 스크립트 정리(2번 항목)도 함께 돌아 로봇 쪽 잔재까지 정리된다.

### 어떻게 구현하는가

**1. 요청/응답 로그**

`id`, 요청 raw, 응답 raw, 처리 시간(ms), 결과(`type`과 `nrc`)를 남긴다. 처리 시간은 P2 한도(50ms) 준수 여부를 보는 지표가 된다.

**2. 로봇 이벤트 로그**

- RTDE 접속과 두절
- `safety_mode` 변화. 값과 전이 방향을 함께 남긴다
- Dashboard 명령과 응답 **원문**. 판정 로직 디버깅에 필요하다
- `robot_busy_owner` 전이

**125Hz RTDE 수신 루프는 로그를 남기지 않는다.** 초당 125줄이 쌓이면 다른 로그가 묻히고 SD 카드도 빨리 닳는다. 두절과 복구 같은 전이만 남긴다.

**3. DTC 설정 / 소거 이력, 로그 파일 작성 구현**

어떤 코드가 언제 어떤 조건으로 설정되고 소거됐는지 남긴다. 로그 레벨을 구분해 상시 운영에서는 요약만, 디버깅 시 상세를 켤 수 있게 한다. 로그 파일 회전을 설정하되 라즈베리파이의 SD 카드 용량과 쓰기 수명을 고려해 보관 기간과 크기를 정한다.

**4. systemd 유닛으로 부팅 자동 시작 / 비정상 종료 자동 재시작**

네트워크 준비 후 자동 시작하도록 유닛 파일을 작성하고, `Restart=always`로 비정상 종료 시 자동 재시작되게 한다. 재시작 간격도 설정한다. 로그는 journald 또는 파일로 연결한다.

**5. 브로커 주소 / 로봇 IP 설정**

브로커 호스트와 포트, 로봇 IP, 로그 레벨, 각종 타임아웃 값을 외부화한다. [config.py](../config.py)를 확장하거나 별도 설정 파일로 분리한다. **로봇 IP는 0x2E로도 변경되므로**(5번 항목) 설정 파일과 영속 계층 중 어느 쪽이 우선인지 명확히 정한다.

**6. 안전 shutdown (모션 정지 → RTDEControl 해제 → offline 발행)**

SIGTERM 수신 시 아래 순서를 지킨다.

1. 모션이 실행 중이면 정지한다
2. `RTDEControlInterface`를 정상 disconnect한다. 좀비 스크립트 방지가 목적이다
3. status 토픽에 `{"state":"offline"}`을 직접 발행한다
4. MQTT를 정상 종료한다

살아 있지만 응답하지 않는 상태(스레드 데드락 등)를 감지할 프로세스 헬스체크 방법도 검토한다.

### 완료 기준

- [ ] 요청 하나를 보내면 요청, 응답, 처리 시간이 한 줄로 추적된다
- [ ] 모션 실행에서 정지까지의 시나리오에서 `robot_busy_owner` 전이가 모두 기록된다
- [ ] Dashboard 명령의 원문 응답이 로그에 남아 판정 근거를 확인할 수 있다
- [ ] 장시간 구동 시 로그가 회전되고 디스크가 차지 않으며, RTDE 수신 루프가 로그를 폭주시키지 않는다
- [ ] 라즈베리파이를 재부팅하면 RCI가 자동으로 떠서 브로커에 접속한다
- [ ] 프로세스를 강제 종료하면 몇 초 내 자동 재시작되고 좀비 스크립트가 정리되어 루틴 실행이 정상 동작한다
- [ ] `systemctl stop` 시 status에 offline이 발행되고 `RTDEControlInterface`가 정상 해제된다
- [ ] 브로커 주소와 로봇 IP를 코드 수정 없이 변경할 수 있다
