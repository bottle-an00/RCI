> 클라우드(웹 진단 앱) 파트 작업 목록과 대칭되는 RCI/UR3 파트의 작업 목록이다. 총 10개 항목이며, 아래 코드블록은 `작업명 <TAB> "설명"` 2열 구조다. 설명 열은 큰따옴표로 묶인 여러 줄이므로 스프레드시트에 붙여넣으면 하나의 셀 안에 줄바꿈이 유지된 채 들어간다.
>
> 서비스 이름과 서브펑션 이름은 UDS(ISO 14229-1) 표기를 그대로 쓴다.

3. 그리퍼 신호 방식 확인 및 0~100% 매핑 캘리브레이션
4. 카메라 연결 테스트 및 camera_link 모듈 구현"
[RCI(기반)] robot_interface - 로봇 통신 계층	"1. RTDE 수신 스레드(출력 레시피 12종, 125Hz, 캐시 TTL 1s, 5s 재접속)

[RCI(기반)] UDS 처리 구현	"1. mqtt_client 
2. 요청 큐 / 우선순위 스케줄러 / uds_server 디스패처 / 상태 저장소

### 서비스 계층

```
[RCI(서비스)] 세션 / 보안 / 리셋(0x10/0x3E/0x27/0x11) 구현	"1. default↔extended 전환, P2/P2* 응답, S3 5s 타이머 및 만료 시 모션 정지 후 일괄 초기화 
2. TesterPresent 처리
3. 고정 Seed/Key 인증과 3회 실패 시 10초 잠금(7F 27 36→37) 
4. 0x11 소프트 리셋(로봇 본체 무영향, 가상 더미 ECU). 0x11 지원 서브펑션 목록 확정 포함"
[RCI(서비스)] 데이터 읽기 / 쓰기(0x22/0x2E) 구현	"1. 0x01xx 상태 DID 16종 인코딩(rad→0.1°, ℃×10, A→mA, m→0.1mm, rad×1000, 빅엔디안 int16 2의 보수) 
2. Dashboard 계열 TTL 5s 캐시, 그리퍼 마지막 명령값 echo
3. 0x2E 쓰기(확장세션+보안, 0xF195 거부, 0xF1A0 쓰기 시 새 IP 재접속)."
[RCI(서비스)] 강제 구동(0x2F) 구현	"1. 0x0201 프로그램 실행 제어(RTDEControl 선disconnect → play → 재생 종료 폴링 감지 후 reuploadScript 재연결) 
2. 0x0202 속도 슬라이더
3. 0x0203 전원 / 브레이크
4. 0x0204 안전 복구(보호정지 후 5s 제약)
5. 0x0206 그리퍼, returnControl DID별 반환 동작 및 세션 종료 / 타임아웃 / 리셋 시 전체 자동 반환."
[RCI(서비스)] 루틴 실행(0x31) 구현	"1. startRoutine
2. requestRoutineResults 폴링(7F 31 78 → 결과 조립), 
3. stopRoutine(큐 최우선 / RID 무관 / 항상 성공)."
[RCI(서비스)] DTC 읽기/쓰기(0x19/0x14) 구현	"1. DTC 저장 JSON
2. statusMask 조회 및 전체 소거
3. dtc_monitor 500ms 주기 감시로 8종 발생 조건 판정(통신두절 / safety_mode 4종 / 과온 / 저전압 / 카메라)
4. 보호정지 발생 시각 기록"
```

## 항목 간 선행 관계

간트차트의 작업 순서는 목록 번호가 아니라 아래 선행 관계를 따른다. 상세 배치는 [일정 계획](UR3_RCI_일정계획.md)을 참조한다.

| 항목 | 선행 항목 | 사유 |
|---|---|---|
| 1 하드웨어 셋업 | 없음 | 나머지 전부의 토대 |
| 2 robot_interface | 1 | RTDE와 Dashboard 접속에 네트워크 구성이 필요 |
| 3 UDS 처리 | 브로커 접속 정보 | 로봇과 무관하므로 1번과 병행 가능 |
| 4 세션 / 보안 / 리셋 | 3 | 디스패처와 상태 저장소 위에 올라간다 |
| 5 데이터 읽기 / 쓰기 | 2, 4 | RTDE 캐시와 세션 / 보안 전제조건 검사를 쓴다 |
| 8 DTC 읽기/쓰기 | 1, 2, 3 | dtc_monitor가 RTDE 캐시와 camera_link를 읽는다 |
| 9 응답 지연, 에러/상태 발행 | 2, 3, 8 | status 전이 발행이 dtc_monitor와 연동된다 |
| 6 강제 구동 | 1, 2, 4, 8, 9 | 0x0203과 0x0204가 responsePending(0x78)을 쓰고, 0x0204의 5초 제약이 dtc_monitor가 기록한 보호정지 발생 시각을 쓴다 |
| 7 루틴 실행 | 2, 3, 4, 6 | 6번과 robot_busy_owner를 공유한다 |
| 10 로깅 및 서비스 운영 구성 | 1 ~ 9 | 전체 동작을 대상으로 한다 |

**8번과 9번을 6번보다 먼저 배치한다.** 목록 순서상으로는 뒤에 있지만, 6번의 0x0203(전원 / 브레이크)과 0x0204(안전 복구)가 9번의 responsePending(0x78) 처리기를 쓰고, 0x0204의 5초 제약 판정이 8번 dtc_monitor가 기록한 보호정지 발생 시각을 참조한다.

## 범위에서 제외한 항목

| 항목 | 사유 |
|---|---|
| RID 0x0304 이미지 캡처 | 3개 문서 모두 가안 상태이고 이미지 전달 채널(HTTP URL / 별도 MQTT 토픽 / 클라우드 스토리지)이 미확정이다. 클라우드 담당과 채널을 합의한 뒤 별도 항목으로 추가한다(요청서 §9 액션 4) |
| 프로토콜 단위 테스트, 실기 검증, 통합 검증 | 본 목록은 구현 범위만 다룬다. 각 항목의 완료 기준에 자체 동작 확인이 포함되어 있으나, 전수 단위 테스트와 클라우드 연동 검증은 구현 완료 후 별도 단계로 편성한다 |
| 클라우드 의존성 마일스톤 | MQTT 브로커 접속 정보 수령, 스키마 상호 확인, 폴링 주기 합의(요청서 §9 액션 1, 2, 3)는 우리 파트 작업이 아니다. 다만 3번 착수의 선행 조건이므로 시작일 산정에 반영한다 |
| URSim 시뮬레이터 환경 구축 | 실기 UR3를 상시 사용할 수 있어 불필요 |
